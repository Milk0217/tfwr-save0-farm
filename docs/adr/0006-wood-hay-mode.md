# 木草模式独立成脚本，物种交给伴生投票

## Status

accepted

## 背景与决策

需求是「要大量木材和干草买基础升级」，外加「保留向日葵来加速无人机」。由此定了两件事：

**1. 独立成 `wood_hay.py`，不复用 `main.py`。**

游戏一次只执行一个文件，而两者的目标互斥：`main.py` 的产业链把干草/木材当耗材烧掉（胡萝卜每株吃 8 干草 + 8 木材），木草模式要的却是净积累。硬塞进一个文件会变成两个模式互相污染的一团，所以宁可重复一份向日葵逻辑。

**2. 木草混合区（96 格）的物种交给伴生投票，放弃棋盘式。**

混合种植已升到 **10×**，而它作用的正好是草 / 灌木 / 树 —— 也就是干草和木材本身。10× 远大于任何产量升级，所以**让物种去迁就请求**比固定种植划算得多。做法是在 `main.py` 上验证过的 Companion Vote 机制：每格读脚下植物的 `get_companion()`，请求落在混合区内就给那格投票，下一轮按票种下。

保留的部分：**36 格向日葵**（无人机 2 倍速的来源）与 **12 格胡萝卜**（只为给向日葵供 1 胡萝卜/株）。

## Considered Options

- **只加大 HAY/WOOD 带面积**：不改机制、只改配比。但 +50% 面积远不如 ×10 倍率，而倍率是免费的。
- **保留棋盘式，只用胡萝卜带投票**：`main.py` 的做法，但那边胡萝卜的请求只有约 22.5% 够得着缓冲带；木草模式里若只靠 12 格胡萝卜投票，命中率更低。
- **整片地都种树**：树比灌木多产木材，但正交相邻会让生长时间翻倍（4 个邻居 = 16 倍）。看似无所谓（生长从来不是瓶颈），实则把 7 秒拉到 112 秒，平均要等约 7 轮才能收一次，**每格每轮产出反而降低**。这条被数据否掉。

## Consequences

- **木草配比不再可控**：请求是三种物种均匀随机，长期看约 1/3 落在草、2/3 落在灌木/树，木材会明显多于干草。需要更多干草时，把 `in_hay_zone` 的默认物种改成草、并限制投票覆盖范围即可。
- 树的相邻惩罚会重新出现（投票不知道棋盘式的存在）。接受，因为生长不是瓶颈，而 10× 的收益远大于它。
- **未验证**：`plant(Entities.Grass)` 是否被允许；以及草的伴生偏好绑在**植株**上还是**格子**上。代码在收割前后各投一次票以同时覆盖两种可能，`mix_plan` 会显示实际拿到指派的格数 —— 如果它长期接近 0，说明草这条路走不通。
- 自动升级**每轮只买一个**，并为木材/干草各留 1500 底数、胡萝卜 500。`upgrade_reserve()` 是唯一需要按需调整的地方。
- 切换模式靠重新运行脚本，`clear()` 会重建棋盘。
