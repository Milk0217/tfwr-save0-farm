# 混合种植只做测量，暂不主动满足伴生

## Status

accepted

## 背景与决策

混合种植给草/灌木/树/胡萝卜的产量乘 **5**（每升一级翻倍）。它看起来是农场里最大的一个乘数，但实测与规则核查后，我们**不主动去满足伴生请求**，只做抽样统计（`companion_survey`）。

三条理由，缺一条这个决定都会翻过来：

1. **它帮不到真正的瓶颈。** 只有 Grass / Bush / Tree / Carrot 有伴生偏好，南瓜与向日葵没有。而当前的目标是 `get_cost(Unlocks.Expand)` 要 **64000 南瓜**（上一级只要 8000）。混合种植只增益已经过剩的干草、木材、胡萝卜。
2. **确认一次命中必须飞过去。** 游戏没有读取远处格子的函数：`get_entity_type()` 只对无人机脚下有效，`measure(direction)` 只返回花瓣/仙人掌尺寸/迷宫宝藏位置。请求坐标最远 3 步，来回约 6 个行动 = 1200 ticks。而且每次收割补种都会**重新随机**请求，所以这个成本每轮都要重付——按 30 株胡萝卜算，一轮扫描要多花约 30%。
3. **5× 的账算不过来。** 把胡萝卜格牺牲掉改成伴生植物，等于用一整格的产出换另一格的 4 倍增益；在 5× 下大约只能打平。要到 10× 以上才有明显净收益。

## Considered Options

- **M2 只为胡萝卜做主动伴生**：读请求 → 飞过去确认 → 不对就改种。倍率 ≥10× 且胡萝卜成为瓶颈时才划算。
- **M3 把左半区改成四物种混合田**：倍率最大化，但放弃 WOOD/HAY/CARROT 的功能带结构，复杂度与风险最高。

## Consequences

- 当前布局下有一部分命中是**白拿的**：胡萝卜的请求恰好指向 HAY 带的草、或 WOOD 带里对种的树/灌木时，加成已经发生，与脚本是否知道无关。`comp_hit` 就是用来量化这部分的。
- 抽样调查每 20 轮跑一次、且放在计时区间之外，开销约 2%。
- 若要改判：先升混合种植等级。倍率到 10× 以上、且胡萝卜变成南瓜/扩张的瓶颈时，M2 才值得做。

## Amendment：改判并实现 M2（倍率升到 10× 之后）

改判条件被触发了：混合种植升到 **10×**，而胡萝卜正是整条链的根（`胡萝卜 → 南瓜 → 仙人掌 → 苹果 → 骨头`），且库存一度掉到 5889、逼近 `CARROT_RESERVE` 门槛。

但**实现方式与原计划的 M2（飞过去逐个满足）完全不同**，因为发现了一个更好的做法：

胡萝卜在 `plant()` **成功之后立刻**就能 `get_companion()` —— 比它被收割早整整一轮。于是把方向倒过来，改成**投票制**：

1. 扫到胡萝卜 → 收割 → 补种 → 读新苗的请求 → 给那个坐标**投一票**（1 tick，不移动）
2. 主扫描顺序 y 从 0 往上，而 WOOD(0~2)/HAY(3~6) 排在 CARROT(7~11) **之前**
3. 所以下一轮**先**按票改种缓冲带、**再**收割胡萝卜 —— 伴生已就位，10 倍直接吃到

**代价从「多 30% 扫描时间」降到接近零**：缓冲带本来就要扫，票是顺手读的，没有任何额外跑腿。唯一的变化是缓冲带上有几格改种成别人要的物种 —— 而那里**先收割再按指派补种**，指派的灌木/树照样产木材、指派的草照样自长产干草，**产出不丢**。

放弃的部分：目标落在 CARROT / PUMPKIN / SUNFLOWER 带内的请求一律不满足（那些格牺牲不起）。几何上这决定了上限 —— 12×12 布局下约 **22.5%** 的请求落在缓冲带内（相邻行 37.5%，中间行接近 0），所以胡萝卜的期望倍率约为 `1 + 9×0.225 ≈ 3.0`。

`companion_survey()`（M1）保留，用来验证改判后的 `comp_hit` 是否真的抬升；上报新增 `comp_plan` 显示本轮生效的指派格数。
