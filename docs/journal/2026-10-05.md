# 2026-10-05 —— 黄金产量冲 2,000,000/分：`maze_gold2.py`（16 座 8x8 小迷宫并行）

## 0. 一句话

用户要求「把黄金产量提升到 2m/min」。现状（`maze_gold.py` v34 实测，2026-10-05 日志）
是 **688,000 金币/分**，差 2.9 倍。本轮**没有**去微调旧脚本，而是先做离线模拟
（`tools/maze_sim*.py` + `maze_mock.py`），查出错在哪，再按结论写了
**新脚本 `maze_gold2.py`**（16 座 8x8 小迷宫、每座 2 架、各自建图走最短路）。
模型预期 **2.8M ~ 6.3M 金币/分**（见 §3），在 2M 目标之上留了余量。

## 1. 旧口径（`maze_gold.py` v34）为什么卡在 688k/分

`_o.txt` 的实测（lv6、32x32、31 架猎人抢同一个宝藏）：

```
[stat] gold ... gain 5373952 elapsed_s 467.53 gold_per_min 688178
[maze] session 结束: 主机收了 8 次 | 平均步数 952.25 最大步数 3322
```

* 164 次宝藏 / 468.5 秒 = **2.86 秒/次**，而一个动作 = 200 tick、引擎 6075 tick/秒
  ⇒ 一次宝藏的预算是 200 tick 的 87 倍 ⇒ **胜者平均要走约 87 步**（若按 94 tick 口径则是 185 步）。
* 瓶颈是**走路**：`measure()` 全场给宝藏坐标（1 tick），`use_item` 一次动作同时
  「收货 + 重定位」（200 tick）。收割本身几乎不花时间。

## 2. 离线模拟查出的两件事（这是本轮的核心发现）

工具：`tools/maze_sim.py`（几何）、`maze_sim2.py`（拆小迷宫）、
`maze_sim3.py`（完整生命周期）、`maze_mock.py`（**把 maze_gold2.py 原样跑在假棋盘上**）。

1. **贪心 DFS 在迷宫里浪费 4~70 倍**：32x32 生成树里，宝藏到「最近的家」的**真实树距离
   平均只有约 10 步**（32 个家的 Voronoi 分布），而现行贪心 DFS 平均要走 **约 700 步**
   ⇒ 实测反推的 87~185 步正好落在两者之间 ⇒ **瓶颈是搜索算法+迷宫尺度，不是无人机数量**。
2. **迷宫的内墙数 = `(k-1)^2`**：k=32 是 **961 面**，而"每次重定位随机拆几面墙"在
   300 次生命周期里拆不完 ⇒ 大迷宫永远绕；**k=8 只有 49 面 ⇒ 会被拆到全开**，
   越刷越顺（小迷宫的结构性复利）。这是「拆小」而不是「多开几架」的真正理由。

`maze_mock.py` 的实测（假棋盘上跑真实脚本，150~700 次宝藏、0 可疑点）：

| 场景 | 实走步数/宝藏 | 家的真实最短路 | 两家的较小值 |
|---|---|---|---|
| 1 架、不复用拆墙 | 16.6 | 17.0 | 8.2 |
| 1 架、每次拆 1 面墙 | 16.6 | 8.8 | 5.5 |
| 1 架、每次拆 2 面墙 | 16.8 | 9.1 | 5.2 |

⇒ **"建图 + BFS 距离场" 把走位压到了理论最短路**（16.6 = 单架漂移时的真实最短路；
若两架都待在自己的家，则降到 5~8 步）。

## 4. 新脚本 `maze_gold2.py` 的设计

| 项 | 做法 |
|---|---|
| 布局 | 32x32 切成 **4x4 = 16 个 8x8 区域**，每区 **2 架**（主机 + 31 副机 = 32） |
| 落点规则 | **开局探针实测**：在两个锚点各建一座 8x8 探针迷宫，走遍 64 格量包围盒，反推平移量 (ox,oy)；两次不一致就**不跑**（打印诊断）。探针必须用**正式边长**，因为"以无人机为中心"的规则平移量 = -k/2，**与尺寸有关**（用 4x4 探针推 8x8 会整体偏 2 格） |
| 建图 | 每架开工前 DFS 走遍自己的 64 格、逐格 `can_move` 四向量出墙，存进 `OPEN[1024]` |
| 走位 | **BFS 距离场**（源 = 宝藏），沿场下坡；`move()` 失败就地记墙并重做距离场（自愈） |
| 分派 | 同区两架里「**我当前位置**到宝藏」≤「队友**家**到宝藏」的那架去；让位那架**趁机走回家**（否则判据失真 —— 这正是 v34"聚拢"的病根） |
| 复用 | 收到金币就继续；`use_item` 不给金币且宝藏**仍在脚下** ⇒ 判"复用 300 次耗尽" ⇒ `harvest` 树篱拆掉 + 回锚点重建 + 重探 |
| 兜底 | `use_item` 不给金币但宝藏**已不在脚下** ⇒ 被同区另一架抢先 ⇒ **绝不 harvest**（在非宝藏处 harvest 会抹掉整座迷宫，v34 踩过两次） |
| 收工 | 每架都盯共享库存 `num_items(Items.Gold) >= goal` ⇒ 一起停（不靠主机通知） |

参数：`GOAL_GAIN = 10000000`（约 5 分钟 @2M/分）；`REG = 8`、`PER_REG = 2`。

```

* 32 架全部 `explore ok 1 cells 64`，**bbox 与设计的区域完全一致**（如 slot 29 → 16 24 .. 23 31）
  ⇒ **16 座 8x8 真的拼满了整盘** ✓ 探测耗时 4.5~6.4 秒（与预算吻合）；
* 稳态：`gold_per_min` 从 398k 爬到 **947k**（139 秒时）就压住了；
* **关键线索**：`power 35332 -> 30873` = **32.3 点/秒**。按"1 点 = 30 个动作 = 6,000 tick"
  折算 ⇒ 32 架 = 6,060 tick/秒/架 ⇒ **所有无人机都在 100% 烧自己的 tick 预算**。
  ⇒ 结论：**产量不是被走位卡住的，是被空转的语句吃掉的。**

## 9. 新工具 `maze_profile.py`：tick 级体检（不开游戏）

用 `sys.settrace` 数**脚本自己执行了多少行**，再按项目标定过的成本换算
（move/harvest/use_item = 200 tick；measure/can_move/get_entity_type = 1 tick；行 ≈ 0.8~1.4 tick）。

v1 的 hunter 追一次宝藏：

| 项 | v1 实测 |
|---|---|
| 总行数 | 3,741 行（其中 **`bfs` 占 1,815 = 49%**，加上 mock 内部调用共 71%） |
| move | 15.7 次 |
| tick | **6,401** = 1.05 秒 |

⇒ 单座上限 0.95 次/秒（16 座 1.87M/分），而实测只有 0.54 次/秒（1.07M/分）——
差的 0.8 秒正是下面三条：

1. **距离场重复计算**：主循环每圈算一次 BFS，hunter 追一次还算第二次（分派一次 + chase 一次）；
2. **`wait_s(0.15)` 空转**：让位那架的检测延迟 ~0.33 秒（BFS 1,440 tick + 等 0.15 秒）；
3. **"两架都不去"的 0.8 秒空档**：旧判据用"我当前位置 vs 队友家"，两架可能同时让位，
   靠 `MAX_KEEP_S = 0.8` 兜底 ⇒ **那 0.8 秒直接就是速率的天花板**。

## 10. v2 的四处改动（都已实测验证）

| 改动 | 做法 | 效果 |
|---|---|---|
| ① 距离场按目标缓存 | `FTX/FTY` + `ensure_field`：目标没换就**不重算** | 消灭每圈的重复 BFS |
| ② 分派改 O(1) 且对称 | 两家各建一张距离场 `DH`/`DO`，判据 `DH[宝藏]` vs `DO[宝藏]`（平手 pair 0 优先） | **不可能两架都不去** ⇒ 空档消失，`MAX_KEEP_S` 退役 |
| ③ 邻居表 `NB/NBT` | 开局算好"这格的四个邻居是谁" | BFS/走位里省掉两次取模 + 比 `OPEN` 的位 |
| ④ **走位改用 LCA 父链（零 BFS）** | 见 §11 | `bfs` 从 1,815 行降到 **0 行** |

空轮询一圈实测只要 **9.8 tick**（620 次/秒）⇒ 反应延迟从 0.33 秒降到毫秒级。

## 11. 核心：用"我家的 BFS 父指针"做 LCA 走位（**零 BFS**）

迷宫本身是**一棵树**，而 `PH`（以我家为根的 BFS 父指针）里任意两点间的唯一路径 =
它们到 **LCA** 的两段。于是每次宝藏只要：

1. 沿 `PH` 把宝藏 T 的祖先链**打标记**（内存操作，约 dist 条语句）；
2. 从当前位置**朝家走**，第一个踩到的标记格就是 LCA —— 这段是物理走位，
   而且**本来就是必经之路**，一点不浪费；
3. 把 T → LCA 的链拉出来**倒着走** ⇒ 到达宝藏。

`route_to()` 只有约 400 行，替代了 1,815 行的 BFS。**正确性已用假棋盘逐条核对**：
120 次随机起点/目标，**步数与真实最短路完全一致（0 个不符）** ✓

> 试过但**否掉**的方案：先走回家再沿父链去宝藏（"route_home"）。它对正确性没问题，
> 但实测走位从 15.7 步涨到 **35.9 步**（回家那段白走）⇒ 比 BFS 版更慢 ✗。LCA 版才对。

## 12. `maze_mock.py` 抓到的两个真 bug（都在 v2 引入，已修）

   而根（我家）的 `PH` 恒为 -1 ⇒ 被当成"到不了" ⇒ chase 空转 16 轮。

700 次长跑（含 2 次"复用 300 次耗尽"重建）现在 **0 可疑点** ✓

## 14. 用户问「为什么不用 32x32 迷宫？大迷宫也能拆墙」——算过了，**结论站得住**

工具：`tools/maze_size_ab.py`（复用 `maze_sim2.py` 的生成树 + 拆墙模型）。

**先纠正我自己：拆墙的收益比我原先估的大得多。** 每拆 1 面墙 ≈ 1 次重定位：

| 迷宫 | 内墙数 | 没拆 | 拆 1/4 | 拆一半 | 全拆开 |
|---|---|---|---|---|---|
| 32x32（32 架） | 961 | 15.1 步 | **4.9** | 4.1 | 3.5 |
| 16x16（8 架） | 225 | 16.7 步 | 4.8 | 4.5 | 3.4 |
| 8x8（2 架） | 49 | 13.2 步 | 5.0 | 3.9 | 3.0 |

⇒ **只要拆掉四分之一，走位就掉到 5 步左右**（3 倍收益）——用户的直觉是对的。

**但"走位"这一项在大迷宫和小迷宫之间是守恒的**：产量 ∝ 面积，而走位 ∝ 每架管多少格
（两种方案都是 1024/32 = **32 格/架**）⇒ 收入 = 面积/步数，两边抵消：

| 方案 | 没拆墙 | 拆 1/4 |
|---|---|---|
| 32x32 x1 座 | 3.30M/分 | 7.53M/分 |
| 16x16 x4 座 | 3.03M/分 | 7.64M/分 |
| **8x8 x16 座** | **3.67M/分** | 7.45M/分 |

**真正的差别在"建图成本"，而且它是决定性的**：

| 方案 | 每架要探多少格 | 建图墙钟 | 一座迷宫寿命（301 次宝藏） | 建图占比 |
|---|---|---|---|---|
| 8x8 x16 座 | 64 格（**32 架各学各的**） | **6.3 秒**（实测 4.5~6.4 ✓） | 约 80~150 秒 | **4~8%** ✓ |
| 16x16 x4 座 | 256 格 | 25 秒 | 约 80 秒 | 约 30% |
| **32x32 x1 座** | **1024 格（32 架把同一张图各学一遍）** | **101 秒** | 约 80 秒 | **>100%** ✗✗ |

⇒ **大迷宫的致命伤不是走路，是"32 架把同一张 1024 格的图各背一遍"**：
小迷宫是 32 架**并行学 16 张不同的图**，大迷宫是 32 架**重复学同一张图**。
一座迷宫只能用 301 次，而背完图它就该过期了 —— 缩到 16x16 就已经吃掉三成时间。

**另外两条不利**：
* **风险集中**：只有一座迷宫时，任何一次卡住都让**全盘**停产（v34 实测主机
  `平均步数 952 / 最大 3322`，就是这种单点故障）；16 座时一次卡住只损失 1/16；
* **v1 那 71% 的语句开销**确实是"大迷宫更划算"的理由（每宝藏 16 倍金币去摊），
  但 **v2 已经把 BFS 干掉了**，这条理由随之消失。

**下一步（想试的话）**：
1. **零成本 A/B**：把 `REG` 改 16、`PER_REG` 改 8 ⇒ 4 座 16x16（模型 5.7M/分，比 8x8 低约 20%）；
2. 真要跑 32x32，必须把"开局整张背图"改成**边走边学**（增量建图 + 曼哈顿分派兜底），

## 16. 【BUG】一座迷宫耗尽时同区两架**抢着重建**，11 架接连退出

```
137 [maze2] slot 30 迷宫耗尽（复用 300 次上限）⇒ 重建
142 [maze2] slot 31 measure None ⇒ 重建          ← 同区 31 也发现了
146 [maze2] slot 30 重建失败 ⇒ 本机退出          ← 它刚建好的迷宫被 31 拆了
150 [maze2] slot 29 重建失败 ⇒ 本机退出
151 [maze2] slot 10 重建失败 ⇒ 本机退出   ...（共 11 架）
```

**根因**：迷宫耗尽时，pair 0 从 `chase` 的 `r == 4` 知道、pair 1 从 `measure() == None`
（或 `r == 3`）知道 ⇒ **两架都去 `destroy_maze + plant + use_item`** ⇒ 互相把对方刚建好的
迷宫抹掉 ⇒ `explore` 收不满 64 格 ⇒ 重建失败 ⇒ **退出**。
退出的代价是**永久**的：那片的产能直接少一半 ⇒ 速率从 3.17M 掉到 3.04M/分并继续走低。

**修法（v2.1）**：新增 `handle_lost()` 作为"迷宫没了/耗尽"的**唯一入口**：
* **只有 pair 0 有权拆和建**；
* pair 1 先 `wait_maze()` 回家等（上限 25 秒），等到了就 `resync_maze()` 重新探图对齐，
  等不到（队友退出了）才自己上；
* 重建失败改成**退避重试 3 次**，不再一次失败就永久退出。

## 17. 顺手挖出的两个同类隐患（都是"跑完整主循环"才暴露的）

1. **`r == 3` 那条缝**：v2.1 第一版只堵了 `measure None` 和 `r == 4`，而 `r == 3`
   （= pair 0 拆迷宫时 pair 1 正在里面走）**还是老的"自己重建"** ⇒ 同一个 bug 会从这条缝
   再钻出来。已把三条路径统一到 `handle_lost()`。
2. **队友失联后会永久让位**：分派规则是对称的（"我家的距离 ≤ 队友家的距离 才去"），
   一旦队友已退出，剩下那架会在"该队友去"的宝藏上**永远等** ⇒ 那片彻底停产。
   在假棋盘上跑完整 worker 主循环时**直接挂住**，就是这么发现的。
   已加 `STALL_S = 1.2` 兜底：同一个宝藏超过 1.2 秒没人拿 ⇒ 我去（正常一次只要约 0.5 秒，
   所以兜底几乎不会触发）。

# 第四轮：v2.1 实跑又抓到一个真 bug（时序握手）⇒ v2.2

## 20. v2.1 的读数：**比 v2 还慢**（峰值 2.82M vs 3.17M），而且 7 架退出

```

## 21. 根因：**握手的时序错了**（日志 148~163 行，region 10）

```
148  slot 20(pair0) 迷宫耗尽
149  slot 21(pair1) 迷宫耗尽
152  slot 21 队友重建好了 ⇒ 重新探图对齐     ← 只隔约 1~2 秒！
157  slot 20 本座寿命内通道数 63 -> 86         ← pair0 的"数墙探图"其实要 5~6 秒
163  slot 21 重新探图失败 ⇒ 本机退出
```

pair 0 收到"耗尽"后要**先探图数墙**（5~6 秒）才拆迷宫 ✗，而那几秒里**旧迷宫还在**、
`measure()` 仍有值 ⇒ pair 1 的 `wait_maze` **立刻返回** ⇒ pair 1 在**旧迷宫**上开始探图，
pair 0 紧接着把迷宫拆掉 ⇒ pair 1 探到迷宫外 ⇒ 收不满 64 格 ⇒ 失败退出 ✗✗

**教训**：`measure() != None` 只能说明"有一座迷宫"，**不能说明"是新那座"**。
跨机握手必须用**状态变化**（消失 → 出现），不能用**状态存在**。

## 22. v2.2 的修法

| # | 改动 | 解决什么 |
|---|---|---|
| 1 | `wait_maze` 改**两阶段**：先等旧迷宫**消失**，再等新迷宫出现（第一阶段 15 秒超时 ⇒ 返回 0 让调用方接管） | 时序握手（本轮的 bug） |
| 2 | `do_rebuild` 走到锚点后先看脚下：迷宫**已经在**就别再种，直接重新对齐 | "你建我拆" |
| 3 | `resync_maze` 探图前先确认"我在迷宫里"，不在就先回家重试 | 站在迷宫外探图会一直打转 |
| 4 | resync 失败改成**退避重试 3 次**（`resync_with_retry`），不再一次就永久退出 | 7 架退出的放大器 |
| 5 | 每步探测 → **隔一步**；"数墙探图" → **每 2 座寿命一次** | 省开销（实测拆墙速率每 14 次重定位才 1 面，每步都探是浪费） |

**新增回归防线**：`tools/maze_wait_test.py` —— 假棋盘只有一架无人机，
**跑不出"同区两架抢重建"的时序** ✗，所以这个 bug 一直漏到实跑。
这个测试用"可编程的世界"把四个关键时序钉死：旧迷宫先消失再重建 ⇒ 1、一直不消失 ⇒ 0、
