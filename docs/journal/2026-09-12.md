### 2.3 由此暴露的**真 bug**：补课在攒一个买不到东西的数

### 2.5 为什么**不**追 Mazes lv6（这是本轮最重要的战略结论）

32×32 满场迷宫一次 = `1024 × 2^(lv-1)`：lv5 = **16,384 金币**，耗 512 个奇异物质。
Leaderboard 要的 100 万金币只要 **61 次迷宫 = 31,232 个物质**，而库存 **3,152 万**。
⇒ **金币线早就不是瓶颈**，花 1560 万仙人掌把金币翻倍没有任何回报。
（旧的「金币 → Megafarm → 多无人机」链条**已经走完了**：Megafarm 已满级 lv5 = 32 架。）

真正的瓶颈现在是**骨头**：Leaderboard 要 200 万（先升 Polyculture lv5 则共 325 万），
库存 85,665，唯一来源是恐龙跑。⇒ **Dinosaurs lv5（259 万仙人掌，几乎白拿）是唯一
有实质回报的一步**：它把产量与成本同时翻倍 ⇒ 单位仙人掌的骨头不变，但**单位时间的骨头翻倍**。

## 3. 任务 2：仙人掌改 32 个矩形 —— **前提被实测推翻，已决定不做**

计划（`docs/plans/cactus-parallel.md`）的推理是「吞吐 ∝ √(区域数)、680 格 ÷ 32 ≈ 21 格/块、
约 1.7 倍」。逐条对账后不成立：

1. **6×6 方阵无法再切**。两块相邻的仙人掌区会被 `swap()` 互踩（计划自己也写了这条自检要求），
   所以区域之间必须留 ≥1 格间隔 —— 而 14 个方阵彼此之间**已经只剩 1 格间隔**，切不动。
2. **「680 格」里的 176 格来自胡萝卜带与木草带**，那些地在方阵之外、只能切成窄条
   （胡萝卜带 8 行 × 16 列：留 1 行间隔后最多 3~4 条），**每块产量小**（1×16 = 1,024/轮），
   加起来的增量很小；木草带还得先 `till` 再还原成草原，风险另算。
3. **吞吐模型漏了每轮的固定开销**。一轮 = 清地 + 播种 + 生长 + 收割 ≈ **4 秒**（与块大小无关）
   + 排序。用实测的 14 块 × 36 格 ≈ 12 秒/轮反推 `S(36) ≈ 8 秒`、`S(n) ∝ n^1.5`，
   代入 `k · 4n² / (F + S(n))`：**块大而少反而更优**，把边角地全用上的上限也只有
   **1.12~1.25×**，不是 1.7×。
4. **收益已经缩水**：补课只差 22.5 万仙人掌，按现有 14 方阵 ≈ **37 秒**跑完；
   1.2× 只能省下 **5~8 秒**。

⇒ 为了 5~8 秒去改已经验证过的排序/搬运代码（`cactus_push_value` 的下标换算、L 形路径安全性），
不划算。**用户已确认跳过。** 结论落进 `docs/plans/cactus-parallel.md` 的「已推翻」一节。

### 11.2 坏消息：紧循环进去 **1 步**就被挡住

```
[dino] v9 tight cycle mode at eaten 28 steps 1742 tail 28
[dino] v9 cycle blocked at step 1743 eaten 28 pos 14 1 tail 28
```

**根因不是新写的循环，而是一个一直潜伏的假设**：紧循环（和 v8 的 `bare_cycle_move`）
都假定无人机在**正向**遍历哈密顿回路。但 B1 阶段的 `cycle_step` 在前向被挡时会
**反向走一格**（`dir_to(CYCLE[(i-1+CELLS)%CELLS])`）—— 而前向被挡的原因通常是
**直走阶段留下的、不在回路上的身体**。一旦反向，无人机就可能一直**倒着**走回路，
此时「回路正向」那一格正是自己的身体 ⇒ 只走正向的紧循环第 1 步就被挡住。

实测位置 `pos 14 1`：该格的正向邻居是 `(13,1)`（行 1 在回路里是从 x=31 递减到 x=1），
被身体占着 ⇒ 说明它就是**从 (13,1) 往东走过来的**，即倒着遍历。

**v8 有同样的缺陷**，只是 22×22 那次运气好没踩上（它撞墙时的处理是
`else: print(...); eaten = target`，也就是**整场白跑**）。22×22 那次能跑完 38,338 步回路，
说明「正向」在那一轮恰好成立。

### 11.3 v10 的修法：进循环前**先判一次方向**，且只允许翻一次

```
	fwd = 1        # 1 = 沿回路正向；0 = 反向
	flips = 0
	...
	if fwd == 1:  d = CYCLE_DIR[ST[9]]; nxt = ST[9] + 1（越界回 0）
	else:         nxt = ST[9] - 1（越界回 CELLS-1）；d = (CYCLE_DIR[nxt] + 2) % 4
	if move(DIRS[d]):  成功 → ST[9] = nxt
	else:
		第一次失败 → 翻转 fwd，打印 [dino] v10 direction flip（沿回路反向走同样是
		             「回路上的一段弧」，安全性证明不变）
		第二次失败 → 两个方向都走不动 = 蛇填满农场 → 正常收工结算
```

反向方向**不需要第二张表**：反向走 `CYCLE[nxt] → CYCLE[ST[9]]`，
其方向就是正向表那一项的反向，而 `DIRS = [N, E, S, W]` 的反向正好是「下标 +2 取模」。

顺带把 `if move(DIRS[d]) == 0:` 改成真值判断 `if move(DIRS[d]):` ——
`move()` 返回的是 True/False，用 `== 0` 去比是在赌「布尔与整数相等」，没必要赌。

验证：`py_compile` 0、静态体检 0 可疑点、可达性 23/23。

## 13. `maze_gold.py` → **v34（迷宫复用版）**

### 13.1 先算账：用户提的「200M 金币/分钟」不存在

```
32x32、lv5：一次宝藏 = 1024 x 2^(5-1) = 16,384 金币
200,000,000 / 60 / 16,384 = 203 次宝藏/秒      ← 目标要求
```
而游戏的时间预算是硬的：**一个动作 = 200 tick**，2 倍速下实测 **6,075 tick/秒**
⇒ 全局 **30 个动作/秒**（所有无人机在同一条时钟上推进，但**动作是并行的**，
`用法 B` 实测 4 座独立小迷宫有 3.7 倍吞吐就是这个证据）。

一次宝藏**理论最少** = 1 步走过去 + 1 次 `use_item` = **400 tick** ⇒ 天花板：

```
6,075 / 400 = 15.2 次/秒 -> 248,832 金币/秒 = 14.9M 金币/分钟   (lv5)
                                            29.9M 金币/分钟   (lv6)
```

⇒ **200M/分钟比"宝藏永远在脚边"这个不可能状态还高 13.4 倍**。
现实区间是 **0.5M ~ 7M/分钟**，取决于墙被拆得多快。

### 13.2 复用的真正价值（我上一节判断错了）

复用不是"省一次 clear"那么简单，而是三件事叠起来：

1. 固定开销（`clear()` + 派 31 架 + 散开 + 走到灌木 + 种 + 灌）**一座迷宫只付一次**；
2. 站上宝藏时 **`use_item` 一次动作 = 收货 + 重定位**（文档原文），
   所以每个宝藏只要 **1 次动作**，不需要先 `harvest` 再重开；
3. **每重定位一次，迷宫的墙会被随机拆掉一些** ⇒ 越用越开阔 ⇒ 每次追捕的步数单调下降。

第 3 条是决定性的：排行榜 `Leaderboards.Maze` 的目标 9,863,168 金币，
文档明说"正好等于复用一座 32x32 迷宫 300 次"—— **这个玩法本来就是为复用设计的**。

### 13.3 v34 的结构

| 角色 | 干什么 |
|---|---|
| 主机 | `clear()` → 派 31 架猎人 → 散开 2 秒 → `goto(8,8)` + `plant(Bush)` + `use_item(物质)` 建迷宫 → **自己也当猎人** → 达标/耗尽 → `destroy_maze()` → `wait_for` 全体 → 下一座 |
| 31 架猎人 | 走向各自的散布起点（**边走边看脚下有没有变成树篱**）→ 追宝藏 → 站上去 `use_item` 收货并重定位 → 继续追下一个 |

**追捕 `hunt()` 的关键设计：**
- **每步重读 `measure()`**（1 tick）：宝藏会被别的猎人挪走；目标一变就
  `GEN[0] + 1` + 清空 DFS 栈，从当前位置重起一次搜索。这是"多机抢同一个宝藏"的必要代价。
- `visited` 用**世代号**（`VIS[k] == GEN[0]`），省掉每次搜索的 1024 条清零语句。
- 死胡同沿 DFS 栈 `step_back` 回退（迷宫是一棵树时这是唯一走法）。

**没有共享内存在这里是好事**：每架猎人重新执行本文件 ⇒ **各自一份 `VIS`/`PATH`/`GEN`**，
零跨机协调。唯一的全局真相是 `num_items(Items.Gold)`，所以报告一律用**金币增量**算，
不用各机自己的计数器（BUILD 13 的假数据坑）。

**机制自愈**：`hunt()` 在宝藏上先试 `use_item`，**用金币增量验证**；没给金币再退回
`harvest()`（文档保证 harvest 宝藏也给金币）。所以即使"use_item 能重定位"与文档不符，
脚本也只会退化成"一座迷宫收一次"的旧行为，**不会卡死也不会算错**。

**两处防死锁闸**（都实测过同类事故，必须留）：
- 主机：连续 `MAX_HUNT_RETRY = 20` 次`hunt()` 返回 0 就拆迷宫收工；
- 猎人：同样计数后 `break` —— 否则迷宫被拆掉后卡在角落的猎人会 `while True` 空转，
  而主机的 `wait_for` **永远等不到**（最难查的一类死锁）。

### 14.2 `cactus_farm.py` —— 整盘铺方阵，一块一架

针对 15,600,000 个仙人掌（= Mazes lv6，**金币/宝藏 16,384 → 32,768，直接把 maze_gold 翻倍**）。

相对 main.py 的 `cactus_push` 三处提速：

1. **整盘铺满**：按 `REG_SIZE+1` 的间距平铺（块间必须留 1 格，否则两块相邻会被 `swap` 互踩）；
2. **省掉冗余的清地遍** —— `cactus_push` 每轮都先走一遍清地，而**上一轮的连锁收割已经把整片收空了**，
   那一遍纯粹是当初为了清南瓜留下的（实测每轮白花 2.4 秒）；
3. **播种时浇水**，带 `WATER_FLOOR` 存量下限保护。

模型（用 14.1 的标定）：

| 配置 | 块数 | 单轮产量 | 单轮耗时 | 合计 |
|---|---|---|---|---|
| REG_SIZE=6 | 16 | 5,184（**已验证**） | ~8.4 s | ~10,000/秒 |
| REG_SIZE=5 | 25 | 2,500（**模型推断**） | ~4.4 s | ~14,000/秒 |
| 现在的 `cactus_push`（14 块 6x6） | 14 | 5,184 | ~12 s | ~6,000/秒 |

默认取 **REG_SIZE=5**；但「4n²」这个产量口径**只在 6x6 上验过**，所以脚本每轮打印
`yield` 与 `cyc_s` —— 若 5x5 的 yield 不是 2,500，就把 `REG_SIZE` 改回 6。
脚本还打印**分阶段耗时**（`phase plant/grow/sort/harv`），把"到底哪一段贵"直接量出来。

每 `VERIFY_EVERY = 10` 轮才做一次**真实的**重读自检（防模型漂移）。

### 14.3 `sun_farm.py` —— 一行一架，32 架

关键事实（**推翻了我之前的错觉**）：

- **收入 = 收割刀数 × 1.68**，不是 ×1.11。实测 `hsum 345.88 / harv 206 = 1.68`，
  因为 206 刀里有 24 刀落在"全场最大花瓣"上吃到 8 倍（`1 + 7 × 24/206 = 1.82`）✓。
- **访问速率受限、不是地块受限**：一来回 = 1 move + 收割 + 补种 ≈ 3 个动作 ≈ 1,000 tick/格
  ⇒ 单机约 6 刀/秒 ⇒ 约 10 电/秒。**加一架就多一份访问速率**。
- 向日葵 5 秒长好，而一圈（32 格）要 1.6~3.2 秒 ⇒ **每次经过都是熟的**。

设计：**一行一架**。32x32 正好 32 行 32 架，每架包一整行；行内循环极简
（查脚下 → 割/补种 → `move(East)`）。**棋盘是环形的，从最右列再往东会绕回最左列**
⇒ 一行天然是闭环，32 步一圈、**零回程开销**（这正是 CONTEXT 里"主遍历必须对齐起手位"那条约束的反面用法）。

模型预期：单机 10~20 刀/秒 ⇒ 32 架 **320~640 刀/秒** ⇒ **约 540~1,070 电/秒**
（现在 main.py 的实际量级只有 ~10 电/秒，因为 78 格的带子只跑了 2 架）。

**浇水默认关**：浇水能把生长从 5 秒压到 1 秒，但**水是产水速率受限的资源**
（watering 满级也只有几十罐/秒），整盘 1024 格每圈浇水要 300+ 罐/秒，
一定把水抽干然后退回更慢的状态。要开就靠 `WATER_FLOOR` 兜底。

**用途提醒**：电量是**存量**资源，本身不直接产粮 —— 它的作用是让后续长跑一直吃 2 倍速。
27,877 已经够 maze_gold 跑约 1.5 小时（32 架 × ~5 动作/秒 ≈ 5.3 电/秒），
所以这个工具主要用于"长时间无人值守前先灌满"。

### 14.4 两个工具共同的纪律

**必须能退出**（写的时候漏了、审的时候补上）：向日葵副机是 `while True`，而主机最后要
`wait_for` 全部 ⇒ 会永久阻塞。用「`num_items(Items.Cactus) >= target`」当共同收工信号 ——

### 15.3 仙人掌地块还有没有优化空间（逐条算过）

**已经拿到的两处（本轮改动）：**
1. **删掉每轮无条件的全阵 `fix_missing`**：`read_grid` 本来就要走一遍全阵并数出
   「读不到的格子数」，所以只在真的读不到时才补种+重试。白跑那一遍要 25 次移动
   ≈ 一轮的 **9%**，而生长是均匀的，绝大多数轮次没有空格。
2. **排不好就不收割**：原来 `sort_region()` 返回 0 时仍然会 `harvest()` ——
   未排序时连锁不扩散，收一刀只有 **1 个**（而不是 4n²），而且会静默污染产量统计。
   现在改成补种+重试（最多 3 次），仍失败就跳过收割。

**剩下的天花板在哪（结论：已经接近模型最优）：**
- 一轮的 **72% 是排序**，而排序的交换次数 = 逆序数 = **相邻交换排序的理论下界**，
  换任何算法都降不下来（只能换"不排序"的思路，但未排序就没有 4n²）。
- **产量 ∝ n²，交换数 ∝ n²** ⇒ 单块吞吐**饱和**（4n²/(a+bn²) → 4/b），
  所以"把块做大"没用；唯一的杠杆是**更多块 = 更多并行**，
  而它被两条硬约束卡住：**32 架无人机上限** 与 **块间必须留 1 格**。
  扫过 REG_SIZE=3/4/5/6，最优就在 4~5（差 1%）。
- 所以下一步真正的杠杆**不在布局上，而在 `Cactus` lv6**：
  `get_cost(Unlocks.Cactus)` = **25,900,000 南瓜**，描述是"Increases the yield **and cost** of cactus"。
  **若 4n² 里的「4」就是仙人掌等级倍率，lv6 会让整条线再翻一倍**（而它吃的是南瓜，
  不是仙人掌 —— 南瓜由 main.py 独立产，~19,000/秒 ⇒ 25.9M 约 23 分钟）。
  ⇒ **这是"用另一条产线的产物换这条产线翻倍"，值得优先做。**（代价：每株仙人掌的南瓜消耗也会涨。）

## 16. **自我纠错**：`4n²` 其实还没被干净地验证过（污染读数）

### 16.1 我上一节犯的错

第 15.1 节我写「cactus +1,000,000 = 16 轮 x 25 块 x 2,500 ⇒ 4n² 对 n=25 也成立」——
**这是循环论证**：「16 轮」这个数本身就是假设每块 2,500 才反推出来的
（若每块 625，则是 64 轮 x 25 x 625 = 1,000,000，**同样精确**）。所以那个 +1,000,000
**证明不了任何产量口径**。

更要紧的是**读数本身是脏的**：
`[cact] yield` 取的是 `num_items(Items.Cactus)` 的差值，而**库存是全局的** ——
25 架同时收割时，每个副机都会把别机的收获算进自己那一轮，倍数约等于同时收割的机数。
**这正是当初 `[pump] pyield` 读出 55,296 = 4 x 13,824 的同一个坑**（见第 9.2 节）。

回头看，**「6x6 = 5,184 = 4 x 1,296」这个"实测"也极可能是同一个污染**：
它是在 BUILD 19~28「N = 4 块并行」期间量的 ⇒ **恰好 4 倍**。而游戏文档写的是
`n` 株同时收割得 `n²` —— 对 6x6 就是 **1,296**。
⇒ 真产量口径到现在为止**仍然未知**，`4n²` 与 `n²` 差 4 倍，而这 4 倍直接决定
「现在的农场是 858k/分钟还是 215k/分钟」。

### 16.2 修法：开局自标定（已写进 `cactus_farm.py`）

在派 25 架之前，**只派 1 架、只跑 1 轮**，那一轮没有任何别的无人机 ⇒ 库存增量是干净的：

```
[cact] CALIB start: 单独一架跑一轮，用来量干净的 per_region yield
[cact] region 0 round 1 yield <真值> cyc_s ... rate ... swaps ... bad 0
[cact] region 0 DONE rounds 1 gained <真值> per_round <真值>
[cact] CALIB end: 上面的 per_round 就是**一块 5 x 5 方阵一次连锁收割的真实产量**
```

实现上给 `worker(idx, target, limit)` 加了 `limit` 参数（>0 = 标定模式，跑满就退），
标定那架用 `limit = 1`。**顺带这也是判断 Cactus lv6 值不值得买的前提。**

另外把**全程速率**改成唯一可信的读数：`(全程库存增量) / (全程墙钟)` ——
每颗仙人掌只被算一次，主机的 `=== cactus_farm end ===` 那行会打出 `cactus_per_min`。

### 16.3 「20M 仙人掌/分钟」的账：不存在这条路

**20,000,000/分钟 = 333,333 个/秒**，而现状约 **14,500 个/秒（≈ 870k/分钟）** ⇒ 差 **23 倍**。

**不可压缩的成本是排序**：交换次数 = 逆序数 = 相邻交换排序的**理论下界**，
实测 `0.0748 n²`（6x6 → 97 次），每次 `swap + move = 400 tick`
⇒ **每颗仙人掌固定要付 `400 x 0.0748n² / (k n²) = 29.92/k` tick**（k = 产量系数 4 或 1）：

| | 每颗 tick | 单机上限（6,075 tick/秒） | 31 架合计 | 折合/分钟 |
|---|---|---|---|---|
| k=4（乐观） | 7.48 | 812/秒 | 25,172/秒 | **1.51M** |
| k=1（文档） | 29.92 | 203/秒 | 6,293/秒 | **378k** |

上面是**假设布局无约束**的天花板；代进真实的铺法约束（两块 5x5 必须相差 >=6 ⇒
32x32 上按 6 间距只能放 5x5 = **25 块**）后：**k=4 → 807k/分钟，k=1 → 203k/分钟**。

⇒ **20M/分钟比"布局无约束的天花板"还高 13 倍，比现实天花板高 25~100 倍。**
这不是优化问题，也不存在"路线"。

### 16.4 顺带扫过的布局最优（结论：已经在最优附近，±15% 以内）

模型 `rate(n) = 4n² / (29.92n² + 296n + 2094)`，配 `k = (32 // (w+1)) x (32 // (h+1))`：

| 区域 | n | 块数 | 合计/秒 |

| 4x4 | 16 | 31（受机数上限） | 13,299 |
| **4x5** | **20** | **30** | **14,610** |
| **3x7** | **21** | **31** | **15,438** |
| 5x5（现在） | 25 | 25 | 13,475 |
| 6x6 | 36 | 16 | 9,776 |

⇒ 换成 3x7（pitch 4x8）模型上只高约 **15%**，而**这已经在模型误差之内**
（"其它动作 296n"那几项是我从两个实测点反推的粗略系数）。
**为了 15% 去重写一套非方形区域的下标运算，在目标差 23 倍的前提下不值得。**

### 17.1 干净的 CALIB 读数（单机单轮）

```

**一块 5x5（25 格）一次连锁收割 = `10,000`。** 而 10,000 = 625 x 16 = **`(格数)² x 2^(cactus_lv-1)`**

> **`cactus_yield = (区域格数)² x 2^(cactus_lv − 1)`**

这条同时解释了当年那条「6x6 = 5,184」：1296 x **4** = 5,184 ⇒ 那时 `Cactus` 是 **lv3**。

⇒ 第 16 节的怀疑成立，**`num_items` 差值在并行下完全不可用于测单块产量**；
唯一干净的就是开局那一次单机单轮（已内置），以及主机最后打印的**全程速率**。
已把并行模式的字段改名为 `yield_raw(污染: 约 = 并行块数 x 真值)`。

## 18. 南瓜的产量口径**被纠正**；新增 `pumpkin_farm.py`（高速产南瓜）

6x6 的连锁收割 = 6² x 6 x 2^(pumpkins_lv − 1) = 216 x 2^(lv−1)
   lv7 -> 216 x 64  = 13,824   ← BUILD 19 当年量到的那个数
   lv9 -> 216 x 256 = 55,296   ← BUILD 42 那批 [pump] pyield 读数（现在 lv9）
```

⇒ **BUILD 42 里那个 55,296 不是"4 架并行污染"，而是等级从 lv7 涨到 lv9 的结果。**
（仙人掌那边的 25x 污染是**实测到**的，但南瓜这条不是 —— 两个 4 倍来源完全不同，
我当时把后者也归给污染，是错的。）
⇒ **交接文档里「`[pump] pyield` 应为 13,824」这条判据已过期，现在应是 55,296。**
⇒ 这也意味着南瓜真实产出是旧口径的 4 倍，专用脚本的收益比按旧值算的大得多。

## 19. `pumpkin_farm` 第一次实跑：**零产出的坑**（已修）+ 改成无缝铺满

### 19.1 根因：`clear()` 之后是**草原**，而草原上的草会被 `can_harvest()` 判成"可收"

```
[pump] block 0 round 1 harvests 1 last_gain(...) 0 cyc_s 4.72 total 8350478
[sun2] rows 0 2 laps 21 harv 100 power 42636.54 pumpkin 8350478     <- pumpkin 全程没动
```

`clear()` 之后整盘是**草原**，草原上长着草 ⇒ `get_entity_type()` 返回 `Entities.Grass`
而且 **`can_harvest()` 是 True**。状态机原来的写法是：

```
if t == None: 补种
elif t == Dead_Pumpkin: 清掉补种
elif can_harvest(): STATE[i] = 1      # <- 草落进这里
```

于是「长着草的空地」被记成「已确认成熟的南瓜」⇒ **第 1 轮就判定整块就绪**，
去 `harvest()` 了一刀草（`last_gain = 0`），16 架随后全部空转。
`cactus_farm` 有 `till_region()`、`sun_farm` 有首圈 `till()`，**只有 `pumpkin_farm` 漏了翻土**。

**修法（两层）**：
1. 访问每格时**先 `if get_ground_type() != Grounds.Soil: till()`**；
2. 给确认那条路加**白名单**：只有 `t == Entities.Pumpkin` 才可能被记成确认，
   草/残留作物一律 `harvest()` 清掉重种 —— 这样同类坑再也不会静默发生。

**另加 CALIB 自检**：单块干净产量 ≤ 0 就直接停下打印警告并 `return`，
不再让 16 架空转一分多钟（这正是这次的实际代价）。

### 19.2 「一直做 32x32 的南瓜会最快吗？」→ **不会，恰好是最慢的之一**

**n>=6 时每格产量恒定**：`n² x 6 x 2^(lv-1) ÷ n² = 6 x 2^(lv-1) = 1,536/格`（lv9）。
所以 32x32 的 1,572,864 = 1024 格 x 1,536 —— **和 6x6 的 55,296 = 36 x 1,536 完全同口径**，
它只是"占地面积大"才数字大。

**而块越大周期越长**：整块要等**最不走运的那一格**（成熟后不再枯死，只需补 20% 的死瓜），
期望等待轮数 = `ln(格数)/ln5`：

| 块 | 格数 | 等待轮数 |
|---|---|---|
| 6x6 | 36 | **2.23** |
| 32x32 | 1024 | **4.31**（近 2 倍） |

总产量一样、周期近 2 倍 ⇒ **32x32 慢约一倍**；而且它只有 **1 个收割门**，31 架没法并行收。

**「6x6 最优」的精确原因**：`n<=5` 走 `n³`（5x5 = 125 = **5/格**），`n>=6` 走 `n²x6`
（6x6 = 216 = **6/格**）—— **6 是吃到好口径的最小边长**，再小掉 20%，再大只是白等。

### 19.3 改成**无缝铺满**（`GAP = 0`）：25 块覆盖 900 格

既然每格产量只跟面积有关，**缝就是白扔的地**。而 BUILD 26 那次「两块 6x6 紧挨连成 6x12」
的实测是 **27,648 = 2 x 13,824** —— **正好面积翻倍、每格不变** ⇒ **紧挨没有惩罚**
（当时说的"产量口径被改变"指的是**读数**变了，不是每格掉了；CONTEXT 里
「矩形口径未验证」这条现在有数据了）。

| 方案 | 块数 | 覆盖格 | 收割门 | G=0.8 模型 |
|---|---|---|---|---|
| 16 块 6x6 + 缝 | 16 | 576 | 16 | 16.7M/分 |
| 16 块 7x7 + 缝（pitch 8） | 16 | 784 | 16 | 18.8M/分 |
| **25 块 6x6 + 无缝（默认）** | **25** | **900** | **25** | **26.1M/分** ✓ |

**为什么最后没做「一块派 2 架」**：收割门要求**整块**待确认数为 0，而每架无人机只有自己的内存
—— 第 2 架不知道第 1 架那半边的状态，门永远不开；唯一解法是让某架扫全块，那就等于回到 1 架。
**无缝多铺几块是同样的收益、且零协调。**

### 19.4 「20M 南瓜/分钟」的账：**够得着，但唯一的杠杆是生长时间**

模型：每周期总产量 = 覆盖格数 x 1,536（与怎么切块无关）；周期 = 收敛轮数 x G + 走位时间。
- `G = 4 秒`：25 块 x 55,296 / 10.3 秒 ≈ 134k/秒 = **8.1M/分**
- `G = 0.8 秒`（浇水足）：≈ **26M/分** ✓ **20M/分 就在这个区间里**

⇒ 周期里 **2/3 是等生长**，所以**浇水（把生长压到 1/5）是唯一的乘数**，
而块大小/布局已经榨到头了。这和仙人掌那边（离上限还差 12 倍、且 `Cactus` 到 lv6 就满级）
**性质完全不同 —— 南瓜这条 20M/分是可达的。**

## 21. 「2000M 草/分钟」的账：**不可能，差 20 倍**

草的唯一来源就是收草，而**种草不需要播种**（草自长）⇒ 每次收获只要 `move + harvest` **2 个动作**。
这是全场**最简单**的一条产线，所以它的上限可以算得很干净：

```
动作预算：32 架 x 6,075 tick/秒 ÷ (2 x 94 tick/格) = 1,034 次收获/秒
再生上限：1024 格 ÷ 再生时间 —— 不浇水(约 5 秒) = 205/秒；浇水到 1.0(约 1 秒) = 1,024/秒
⇒ 取较小者 ≈ 1,024 次/秒
```

每次收获的产量 = 草基础值（`Grass` lv10 满级）x `Polyculture` 倍率（lv5 -> x160，**且该格的伴生请求被满足**）：

| 单次产量 | 假设 | 上限/分 |
|---|---|---|
| 640 | 基础 4 x 160 | **0.7M** |
| 1,600 | 基础 10 x 160（全命中） | **1.6M** |
| 200 | 基础 4 x 有效 x49（伴生命中率约 30%） | **0.2M** |

**绝对天花板 ≈ 99M/分**（1,034 x 1,600），而 **2000M/分 = 33,333,333/秒，比它还高 20 倍**。

⇒ **不存在这条路。** 对比一下三个目标的性质：
- **仙人掌 20M/分**：差 12 倍（`Cactus` 到 lv6 就满级，没有第二级翻倍）
- **南瓜 20M/分**：**可达**（模型 19M/分 @ G=0.8）
- **草 2000M/分**：差 20 倍（比"南瓜可达"的那个数还高 100 倍）

**唯一能做的**是同方向的极限：`wood_hay.py` 已经是"木草模式"（把除向日葵外的全部土地投入
木材与干草），把草铺满全盘、全 32 架只做「走 + 收」、浇水拉满再生 —— 上限就是上面那张表。

> ⚠️ **上面整节作废** —— 第 22 节推翻了它：那个"1,600/次"是我**猜的**，而它是唯一的未知数。

## 24. **伴生倍率是草产量最大的杠杆：约 14~20 倍**

### 24.1 致命事实：**纯草田里，没有任何一格能满足伴生**

⇒ 一片全是草的地里，每一格的请求都是"灌木/树/胡萝卜"，而周围**全是草** ⇒
**永远不可能被满足** ⇒ 纯草田拿到的是 **x1**，把 **x160 整个丢掉了**。
这就是 `hay_farm.py` v1 的结构性缺陷。

### 24.2 关键好消息：伴生一旦摆好就是**永久**的

⇒ 只需要那格里**有那个物种**，长没长好无所谓；
而**草不需要播种**（割完自己长回来）⇒ **请求不会变** ⇒ **布局是一次性的，之后永久吃倍率** ✓✓

### 24.3 最优混合比（模型）

设草的比例 f。草的请求落在"3 步以内"的某个格子、物种在 3 种里随机
⇒ 落在**非草格**上的概率 ≈ (1−f)，而那一格只持有一个物种 ⇒ 平均 1/3 命中：

```
满足率 s ≈ (1-f)/3
相对纯草田的倍数 = f x (1 + 159 x s) = f x (1 + 53(1-f))
最大值在 f ≈ 0.51 -> **13.8 倍**      （本存档实测 comp_hit 18/81 = 22% ≈ (1-f)/3，f≈0.34，吻合）
若能自适应地选"被请求最多的那个物种"（命中率 1/3 -> ~1/2）-> **20.4 倍**
```

## 26. 木产线 92.6M/分 的根因 = trees.md 的**树邻居生长惩罚**（本轮最大发现）

> take `2*2*2*2 = 16` times longer to grow."
> 提示段：用 `%` 判偶。

**v4 布局 = 棋盘格**（树只种 `(x+y)%2==0`，512 棵，每棵东南西北全空 ⇒ x1 生长）。
这是"零树邻居"下网格的**最大独立集** ⇒ 最优密度。

## 29. 南瓜 20M/分 **达成**（v4：块主长驻 + 零同步）

**用户指出的关键**：v3 的 `main` 里有一个我自己造的**全局屏障** ——
```python
tend(0, 1, a0, 1)
wait_for all closers      # ★ 等全部 32 架
wait_for all anchors      # ★
```
⇒ 一块早干完也要等最慢那块 ⇒ **周期 = 最慢那块**（实测 cycle_s 9.4~12.2 秒，而单架版只要 8.8 秒）。
这正是我在 v2 里批评过、却在 v3 里重新造出来的东西 ✗

**v4 的结构**（`pumpkin_farm4.py`）：**每个块一个长驻"块主"，自己循环、永不等待别人**。
```python
def owner(b, with_helper):        # 长驻无限循环
    while True:
        if 目标到了: return
        d = spawn_drone(tend_half, b, 1)      # 派自己那块的后半块帮手
        tend_half(b, 0)                       # 自己管前半块
        while has_finished(d) == False: pass  # 只等**自己这块**
        if wait_for(d) == 0: harvest_block(b)
```
无人机配额：**15 块 ×(1 块主 + 1 帮手) + 1 块 ×1 块主 = 31 架 helper + 主线 = 32 = cap** ✓
（16×2 = 32 再加主线就 33 了 ⇒ 最后一块只能 1 架独占。）

⇒ **南瓜速率 20M/分 达成** ✓（用户确认）

**通用教训**：**并行系统里任何"等所有人"的同步点都会把平均值变成最大值。**
唯一例外是**真依赖**（例如仙人掌的"列排序依赖所有行已排好"）—— 那时屏障必须留。

## 31. 仙人掌 20M/分 **达成**（整片 32×32，34.84M/分）

### 31.1 我错了两轮的"天花板"

我算过两次"仙人掌天花板 ~1.5M 分 / 2.5M 分"，**都错在把 n 锁死在 25**（25 块 × 5×5 布局）。
而文档写的是：

> "You will receive cactus equal to the **number of harvested cacti squared**"
> "if a square of grown cacti is sorted by size and you harvest one cactus, it will harvest the **entire square**"

⇒ **产量 = n² × 等级倍率（lv6 = ×32）**，而 n = **一次连锁收割到的棵数** ⇒ 整片 32×32 ⇒ n = 1,024
⇒ 一刀 **1,024² × 32 = 33,554,432**（实测分毫不差 ✓）

| | 25 块 × 5×5 | **整片 32×32** |
|---|---|---|
| 每格产量 | 10,000/25 = 400 | 33,554,432/1024 = **32,768**（82 倍）|
| 每格成本 | 约 5.4 动作 | 约 47 动作（8.7 倍）|
| 净收益 | — | **约 +9 倍** ✓ |

**⇒ 核心教训：产量是 n² 时，任何把 n 锁小的"并行化"都是在把二次收益拆成线性收益。**
（用 31 架去并行 25 个小方块 = 把 n² 拆成 25 份 n=5 的线性收益 ✗）

### 31.2 实现：`cactus_big.py`

```
阶段一 播种：31 架各一行 + 主线一行（全盘翻土 + 种）
阶段二 逐行排序：31 架各一行 + 主线一行      ← **屏障必需**（列排序依赖所有行已排好 = 真依赖）
阶段三 逐列排序：31 架各一列 + 主线一列
阶段四 收割：走到 (0,0) 割一刀 ⇒ 连锁收空整片
```

**排序用文档 Hint 1**："If the rows are already sorted, sorting the columns will not unsort the rows."
⇒ 先行后列 ⇒ 结果"每格 ≤ 右邻 且 ≤ 下邻" = 文档的 sorted 定义（North/East 更大、South/West 更小）✓

### 31.3 那一刀 2 倍加速：把"无人机位置"做成不变式

```python
# 旧（每交换 4 个动作）：goto(i-1) 走 2 格回来 + swap(East) + move(East)
# 新（每交换 2 个动作）：
goto(1, y); i = 1
while i < N:
    if measure(West) <= measure():      # 查询 1 tick，比较免费
        move(East); i += 1
    else:
        swap(West); move(West); i -= 1  # **swap + move 两步，位置自动落到新 i**
        if i < 1: i = 1; move(East)
```
**不变式：无人机位置 ≡ i** ⇒ 比较只用 `measure(West)`/`measure()`，不需要任何"走过去看"✓

| | 优化前 | 优化后 |
|---|---|---|
| 行排序 | 51.45 秒 | **30.55** |
| 列排序 | 32.54 秒 | **20.85** |
| 合计 | 91.43 秒 | **57.79** |
| 速率 | 22.02M/分 | **34.84M/分** |

### 31.4 这条线真正的极限：逆序数

相邻交换排序的**硬下界 = 逆序数**（32 格随机排列 ≈ 248 次交换/行）。
一行下界 = 248×2（swap+move）+ 280（前进）= **776 个动作 = 25.5 秒**；实测 30.55 秒（高 20%）。
⇒ 两阶段合计约 51 秒 + 播种 5.3 + 收割 1.1 = **57 秒** ← 与实测 57.79 吻合 ✓
⇒ **两阶段方案已榨干；再快只能减少交换次数，而尺寸是随机的 ⇒ 不可能** ✗

**同一算法在不同尺度下的胜负会反转**（值得记）：
* 5×5 小方块里，"目标驱动 + `push_value` L 形推送"**最快**（46 次交换 / sort 7.49 秒）；
  两阶段冒泡在那种尺度下**更慢**（12.3 秒，因为要逐列把整块再走一遍）。
* 整片 32×32 里 `push_value` 的 L 形推送会退化成 O(n²) 走位 ⇒ 两阶段才是唯一可行 ✓

### 31.5 试过并否掉的排序实现（都在 5×5 尺度上实测）

| 实现 | swaps | sort | 产量 | 结论 |
|---|---|---|---|---|
| 目标驱动 + `push_value` | 46~51 | **7.49 秒** | 10,000 ✓ | **5×5 下最快** |
| 跨行主序单趟 gnome | **101** | 21.39 秒 | **32** ✗ | 全废（行末横穿打乱已排好的行）|
| 先行后列两阶段冒泡 | 38~61 | 12.63 秒 | 10,000 ✓ | 正确但更慢（走位翻倍）|

**⇒ `push_value` 的"把每个值沿 L 形路径直接送到确切目标下标"比冒泡更省交换**
（我一度以为"46 = 逆序数下界"，被 gnome 的 101 次交换反证 ✗）

## 32. 全流程教训汇总（可以当清单用）

1. **先量后改**。南瓜九次尝试里五次砍了只值 **1 tick** 的查询、两次砍错了结构；真正有效的改动全部是"先量出 tick 分布/成本表"之后做的。
2. **查询免费 ⇒ 优化查询注定无效**（1 tick vs 走位 200 tick）。
3. **不要造多余屏障**（南瓜 v3 的全局 `wait_for` 把 20M 拖成 14.7M）；但**真依赖的屏障要留**（仙人掌行列两阶段）。
4. **目标必须相对开局库存**（绝对目标连栽两次：wood 设 1e9 而开局 1.33B、carrot 设 4e8 而开局 3.98e8 ⇒ 都第 10 圈就收工，平均值被启动期拖成假数）。
5. **判据要同时看实体**：死瓜/枯死植物的 `can_harvest()` 永远是 False ⇒ 只以它为准的循环会卡死（`probe_pump` 实测踩到）；而 clear() 后的草原上它恒为 True ⇒ 会把空地当成熟作物（pumpkin v2 全场零产出）。
6. **时间戳调度只在"轮次间隔 < 生长时间"时有效**（我们那里轮次 2 秒 ≫ 生长 0.14 秒 ⇒ 连栽三次）。
7. **标定必须自己造条件**：土壤上量再生（草原上量到的是草）、按 `get_companion()` 摆好伴生再量（否则产量随机）、单机单格量（`num_items` 是全局库存，多机同时收割会污染）。
8. **`n²` 型产量不要用小块并行**（仙人掌：整片 vs 分块 = 82 倍/格）。
9. **改代码一律用完整原文锚点 + 命中断言，绝不用位置切片**（我两次栽在这：切片误删全局 `TILLED`/`CYC`；补丁文本漏换行把 `def` 粘进注释）。
10. **检查工具是防线**：`py_compile` / `gamelang`（本语言没有三元表达式！）/ `audit_save0`（未解析名字）/ `deadcode`。这四道在我犯的每一次错上都报过警。
