# 经验沉淀 2026-09-12：从「靠猜」到「问游戏」——以及怎么安全地删代码

> 承接 `lessons-2026-09-11.md`。那一份讲的是**改游戏脚本的铁律**；这一份讲
> **怎么不让错误的结论活过一天**，以及**批量删代码的正确姿势**。

## 一、能用 API 问出来的数，不许写进注释当「估计」

这一轮最贵的教训。上一轮交接文档里的「任务 1」整条链都是猜的：

| 注释里的说法 | `get_cost()` 的实测 | 差多少 |
|---|---|---|
| 「Mazes 下一级 72,000 仙人掌」 | **15,600,000** | 217 倍 |
| 「Megafarm lv4 要 128,000 金币」 | Megafarm **已满级**（无需再买） | 整条路线已作废 |
| 「补课该不该继续，取决于真实成本」 | 恐龙档 2,590,000，而库存已有 2,364,726 | 差 22.5 万，37 秒的事 |

**根因不是算错，是「问题本身没被回答就往下走」**：上一轮留了一句
「重启看 WARNING 拿真实数字」，而那个数字花 10 秒钟写个探针就能拿到，而且能顺带
把**全场**的下一级价格一次问完。

**做法固化**：
1. 任何「要不要继续做 X」的判断，先问自己**哪个 API 能直接给出这个数**；
2. 探针一次问全，不要「一次只回答一个数」（`probe7.py` 用 `get_cost(t, level)` 往后看 3 级，
   同时判出**价格**和**上限**：空 dict = 该级不存在，`None` = 已满级）；
3. 读数落进 `CONTEXT.md` 的「当前存档状态」一节，**下一轮谁都不许再猜**。

## 二、计划里的性能模型必须能对上「已实测的那一个点」

`plans/cactus-parallel.md` 用「吞吐 ∝ √(区域数)」推出 1.7 倍。这个模型有两个洞：

1. **漏了每轮的固定开销**。一轮 = 清地 + 播种 + 生长 + 收割 ≈ 4 秒，与块大小无关。
   加上它之后 `k · 4n² / (F + S(n))` 的极值偏向**块大而少**，与计划的结论相反。
2. **没有回头对账实测值**。实测 14 块 × 36 格 ≈ 12 秒/轮，这**一个点**就足以反推
   `S(36) ≈ 8 秒`，再把 `S(n) ∝ n^1.5` 代进去，立刻能看出 1.7× 站不住
   （把所有边角地都用上也只有 1.12~1.25×）。

**规则**：写性能计划时，**必须先让模型精确复现一个已知实测点**（这里是「14×36 格 / 12 秒」），
对不上就先修模型，别急着写改造清单。附带一条：模型给出的倍数要换算成**绝对时间**
再看值不值 —— 「1.7×」听着很大，「省 5~8 秒」听着就不用做了。

## 三、几何/结构约束要在计划阶段就验，不要留到实现

计划说「680 格 ÷ 32 ≈ 每块 21 格」，但没检查一个硬约束：
**相邻的两块仙人掌会被 `swap()` 互踩**（计划自己在校验清单里要求了这条自检，
却没拿它去卡「切法」本身）。14 个方阵之间只剩 1 格间隔，**根本切不动**；
剩下的只有方阵之外的边角地。⇒ 目标（32 块）在几何上就不可达。

**规则**：把「自检项」提前当**约束求解器**用 —— 如果一条自检会在实现后否决方案，
那它应该在选方案时就参与筛选。

## 四、删死代码要靠可达性分析，不靠人眼

main.py 里同时躺着**四套历史路径**（单机 / 4 架 / 8 架 / 32 架），
人眼看「谁还被谁调用」在这个规模上一定会漏。做法：

1. 扫顶格 `def` → 每段函数体里出现的已知函数名 = 一条调用边；
2. 入口 = `main8` + 顶层语句引用到的名字；
3. 从入口做可达性搜索 → 不可达的即死代码；
4. **先只报告、再产出 spec、最后由「锚点+命中数」的落盘工具执行** —— 三步分离，
   每一步都能单独核对。

**两个必须注意的坑**（都是实测踩出来的漏报）：

- **函数体里的注释也要剥掉**。本项目注释里到处写 `main.py`、`game_loop`、`work_pumpkin`，
  不剥就会把这些死代码「撑活」（第一版漏报了 3 个）。
- **`模块名.函数名` 不能被当成调用边**。`spawn_drone(w_pumpkin.loop_pumpkin_smart, …)` 里的
  `loop_pumpkin_smart` 与主控里那个**已死的同名函数**撞名，认下去就会漏报（第二版漏报 2 个）。
  剥掉 `a.b` 里的 `.b` 即可（顺带解决 `Items.Cactus` / `Unlocks.Mazes` 这类枚举）。

**收益是复合的**：删掉的不只是行数，而是**陷阱**。旧 `work_pumpkin()` 只数第 0 号方阵、
`replant_pumpkin_band()` 会把 14 片一起补 —— 留着它们，未来某次「顺手复用」就是一次
「南瓜只收一片」的静默故障。

## 五、顺手挖地雷：递归代替降级

`init_board_v3()` / `run_one_sweep4()` 的头部都写着：

```
if drone_cap() < 4:
	run_one_sweep4(sweep)      # ← 自己调自己
	return
```

这显然是「本来想调用降级路径、结果写成了自己」的编辑残留，`cap < 4` 时会直接爆栈。
**凡是 `if <条件>: <自己>()` 这种形状，都要当成地雷处理**（要么改成真的降级，要么显式报错）。

## 六、静态检查工具本身要维护：假阳性会让人忽略真信号

这一轮为了跑出「0 可疑点」，修了 3 处**工具**的问题（而不是代码的问题）：

1. `str` 是游戏内置函数，但不在体检工具的 `BUILTIN` 表里 ⇒ 误报「未定义名字」；
2. `import layout` 引入的模块名 `layout` 本身不是变量 ⇒ 误报；
3. 删掉主控里的 `loop_pumpkin_smart` 后，`w_pumpkin.loop_pumpkin_smart` 的属性名被当成裸名字 ⇒ 误报。

**规则**：体检工具一旦开始误报，人就会开始「习惯性忽略」——那比没有工具更危险。
每次误报都要**修工具**，并把它记进工具的注释里（本项目三个工具的注释里都写明了
「第一版/第二版为什么漏报」，就是为了下次别再犯）。

## 七、落盘纪律的补强（`patch_lines.py` 这一轮抓到的两次真问题）

1. **守卫要对「最后一个非空行」判断**：删除区间尾部常带空行（删完不留空行），
   若拿 `lines[end]` 去比对 `last_contains`，空行会让守卫**永远失败**（实测 ABORT 一次，
   文件没被改动 —— 这正是想要的行为）。
2. **md 文档是 CRLF、`.py` 是 LF**：不要用「遇到 CR 就 ABORT」把文档挡在门外；
   检测行尾风格、处理时统一 `\n`、写回时还原。**`.py` 仍然必须 LF**（游戏侧要求）。

**「任何一个 op 对不上就整份不写」这条设计是对的**：本轮 35 个 op 的补丁在第一次尝试时
因为一个守卫失败而整体中止，没有产生半个补丁。
