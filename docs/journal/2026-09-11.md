## 第 5 轮：修掉向日葵遍历 bug + 混合种植调查（M1）

### 发现并修掉的自己的 bug（严重）
12×12 那一轮的遥测出现 `sunflowers 18`（应为 36）。根因：向日葵带遍历用 `move(East)` 连走换格，而**环形棋盘上从 x=11 再往东会绕回 x=0**，于是第 2/4/6 行整行错位到左半区的**胡萝卜带**上；第二遍还会把那 18 格胡萝卜收割掉改种向日葵，主扫描下一轮又改回来 —— 每轮互相踩。
修复：新增 `sunflower_tile_x(row, col)` 做**蛇形走位**（偶数行自西向东、奇数行自东向西），坐标显式计算，用 `goto` 定位。教训：**环形棋盘上任何"连走 N 步覆盖 N 格"的遍历都必须显式算坐标**。

### 仙人掌机制要点
- 尺寸 0~9；有序条件 = **N/E 邻居 ≥ 自己 且 S/W 邻居 ≤ 自己**（棕色无序、绿色有序）
- 收获 n 株 → **n²** 个；s×s 方阵 → **s⁴** 个、**每格 s²**（全场唯一平方增长，南瓜封顶 6/格）
- `measure(direction)` 可原地读相邻尺寸 → 检查违规不用移动
- 排序只能相邻 `swap()`，且每次补种**重新随机**尺寸 → 成本每周期重付

### 决定：不做永久仙人掌带，只做一次性补课（ADR 0005）
理由：恐龙只要 2000 个且之后无下游；6×6 一轮 1296，两轮够；临时征用南瓜带（本就是耕好的 6×6）跑完自动种回南瓜。

### 代码改动（`main.py`）
- 新增 `cactus_x()`、`cactus_plant_and_wait()`、`sort_cacti()`、`cactus_cycle()`、`cactus_needed_for_dinosaurs()`、`cactus_push()`
- **排序终止性可证**：势能 `P = Σ 尺寸 × (x + y)`，每次修复性交换使 P 至少 +1，P 有上界 → 交换次数有限；终止即全盘有序。实现在 `sort_cacti()`，每格只查 E/N（S/W 由邻居自己的检查覆盖），通过数封顶 200。
- 触发完全状态驱动：`num_items(Items.Cactus) < get_cost(Unlocks.Dinosaurs)`，恐龙一解锁自动停止
- 安全阀：`CACTUS_PUMPKIN_RESERVE = 300`（南瓜不足不让位）、`CACTUS_MAX_CYCLES = 12`、`cactus_plant_and_wait` 内「南瓜 < 100 立刻退出」、等待成熟最多 40 遍

### M2 的关键设计反转：从「追请求」到「投票指派」
原计划：扫到胡萝卜 → 读请求 → **飞过去**确认/改种（代价 +30% 扫描时间）。
实际实现利用了文档里一句话：**`plant()` 成功后立刻就能 `get_companion()`**，比该株被收割早整整一轮。于是：
1. 扫到胡萝卜 → 收割 → 补种 → 读新苗请求 → 给目标坐标**投一票**（1 tick，不移动）
2. 主扫描顺序 y 从 0 往上，**WOOD(y 0~2) 与 HAY(y 3~6) 排在 CARROT(y 7~11) 之前**
3. 下一轮**先**按票改种缓冲带、**再**收割胡萝卜 → 伴生已就位，10 倍直接吃到
→ **零额外移动**；缓冲带「先收割再按指派补种」，所以产出不丢（指派的灌木/树照样产木材，指派的草照样自长产干草）。

## 第 8 轮：自动升级 + 专用木草模式（wood_hay.py）

3. **新建 `wood_hay.py`**（专用木草模式，ADR 0006）：
   - 布局 12×12：左半区 72 格 = 木草混合区（默认草）；右半区 y0~3 共 24 格 = 木草混合区（默认棋盘式 Tree/Bush）；右半区 y4~5 共 12 格 = 胡萝卜（**只为给向日葵供种**，且**不施肥**，因为这个脚本要的就是胡萝卜）；右半区 y6~11 共 36 格 = **向日葵（保留，维持 Power 2 倍速）**。

## 第 9 轮：probe4 结果 → 基础升级的交叉依赖与最优配比

### probe4 实测（12×12）
```
num Hay 31374 / Wood 114886 / Carrot 5181 / Pumpkin 11718 / Power 275.23
next Grass       -> Items.Wood 312000
next Trees       -> Items.Hay  307000
next Watering    -> Items.Wood 205000
next Carrots     -> Items.Wood 156000
next Pumpkins    -> Items.Carrot 256000
next Polyculture -> Items.Bone 10000
next Speed / Sunflowers / Fertilizer -> dict_size 0（空成本）
lv Grass 6 / Trees 6 / Speed 5 / Watering 6 / Sunflowers 1 / Polyculture 1
Error: get_cost() 不接受 Items.Wood —— get_cost 只收 Entity / Unlock
```

### 三条关键结论
1. **交叉依赖**：草升级吃**木材**（31.2 万），树升级吃**干草**（30.7 万），正好反过来。这就是「需要大量木头和草」的真实结构。
2. **最优配比可推导**：木材需求 67.3 万（Grass+Watering+Carrots）、干草需求 30.7 万 → **2.19:1**；而每格每轮产量木:草 ≈ 40:18 = **2.22:1**。两者几乎相等 → **木草各占一半格数**时产出比正好对上需求比。当前 `wood_hay.py` 的默认（左半区 72 格草 + 右半区 24 格木）是**偏草**的，但伴生投票会把约 2/3 的受票格推向灌木/树（偏木），两者叠加后的实际配比只能靠遥测确认。
3. **Polyculture 升级要 10,000 骨头** → 想把混合种植从当前倍率升到 20×，**必须先开恐龙线**。这把「木草→升级」和「恐龙→骨头」两条线接上了。

### 顺手修掉
- `can_afford()` 对**空成本字典**原本返回 False → 那三个 `dict_size 0` 的升级（Speed / Sunflowers / Fertilizer）永远不会被尝试。改为返回 True：空成本意味着免费或已满级，让它去试 `unlock()`，**失败只花 1 tick，成功就白拿一个升级**。已同时打进 `main.py` 与 `wood_hay.py`。
- `trade()` 的成本无法用 `get_cost` 查询（不接受 Item 参数），其语义**至今未验证**，代码中不使用。

### 待验证 / 下一步
- `wood_hay.py` 跑两条 `[stat]` 得到木/草**每轮净增**，据此把混合区调成「木草各半」的实际配比。
- `mix_plan` / `mix_hit` 确认伴生投票在木草模式下真的成立。
- 若确认成立，木草产能可再乘上混合种植的倍率 —— 这是通往 30 万级升级成本的唯一现实路径。

## 第 10 轮：转向南瓜/胡萝卜 + 仙人掌排序 v2 + 浇水阈值

### 用户三条需求
1. 现在要大量**南瓜**（`Expand` 64000）和大量**胡萝卜**（`Pumpkins` 升级 256000）
2. 仙人掌排序代码可以优化
3. 浇水阈值能不能提高到 0.5 以上

### 浇水的答案（纯算术，有硬上限和可持续上限两个数）
- 1 罐 = **0.25** 含水量 → 水位只能在 `[阈值, 阈值+0.25]` 之间锯齿 → **阈值 > 0.75 会溢出浪费，这是理论上限**
- 生长速度 含水量 0 时 1 倍 → 1 时 5 倍
- 但真正的约束是**产水速率**：`watering_6` = 32 罐/10 秒 = **3.2 罐/秒**
  - 阈值 0.5（102 格土壤）耗 **2.53 罐/秒** ✓ 有余
  - 阈值 0.75 耗 **3.55 罐/秒** ✗ 会抽干库存（4413 罐约 3.5 小时见底）
  - → **可持续上限约 0.6**
- **而提高阈值换不来任何产出**：生长从来不是瓶颈（扫描 18~26 秒 ≫ 生长 2~7 秒）。已定：`WATER_THRESHOLD = 0.6`，并把 `water` 加进遥测以便亲眼确认库存涨跌。

### 布局与策略调整（服务南瓜/胡萝卜）
- `WOOD_ROWS`：`SIZE//4`(3) → **`SIZE//6`(2)** → WOOD 从 18 格缩到 **12 格**（木材 11 万严重过剩），左半区变成 **WOOD 12 / HAY 24 / CARROT 36**（胡萝卜 30 → 36 格）。
- `CARROT_RESERVE`：5000 → **30000** → **施肥停手**。施肥会把一半胡萝卜变成奇异物质，与"攒 25.6 万胡萝卜"直接冲突，而奇异物质已有约 2.5 万。

### 仙人掌排序 v2（用户要求）
v1 是边扫边修的局部修复循环，每收敛一遍要把 36 格重走一次、通常十几遍。v2 拆成「看」与「动」：
1. `cactus_read_grid()` **蛇形读一遍**进内存（行间只花 1 次移动）
2. 纯内存插入排序求升序目标（零行动开销）
3. `cactus_push_value()` 只执行必要的相邻交换，走 **L 形路径**（先沿行对齐列、再沿列对齐行）—— 该路径经过的格子行主序下标都 ≥ 目标位，**绝不会推动已归位的前半段**
4. 逐位置在「还没归位那半边」里找**最近**的持有者（`scan > idx`）
5. 读不到尺寸（空位/未成熟）时**回退 v1**，保证不白跑

**诚实的结论**：交换次数由随机数据的逆序数决定，这是任何正确排序都绕不开的下界，v2 省的是**反复扫描**开销，预计整体约 2 倍 —— 而仙人掌补课是一次性的（两轮共约 1 分钟），所以这个优化的绝对收益只有几十秒。已把这个判断告诉用户。

**踩到的坑（已修）**：用 PowerShell 做 `\tsort_cacti()` → `\tsort_cacti_v2()` 的全局替换时，把 v2 内部**回退到 v1 的那一行**（两个 tab 缩进，也包含 `\tsort_cacti()` 子串）一起替换了 → **无限递归**。教训：**用字符串替换改代码时，要检查被替换串是否是更长匹配的子串**。

### 新增遥测字段
`water`（水量库存）、`cactus_swaps`（本周期实际交换次数）、`cactus_empty`（读不到尺寸的空格数）。

## 第 12 轮：max_drones = 2 → 双无人机并行（按列切）

### 用户输入

### 核心设计约束（文档 No Shared Memory）
**每架无人机有自己的内存，读不到别人的全局变量。** 而 **Companion Vote 的指派表 `PLAN` 就存在内存里** → 「投票者」（左半区胡萝卜/草/树/灌木）与「被指派目标格」（左半区 WOOD/HAY）**必须同机**。

- **按列切**（左半/右半）→ 两者同属左半区 → **投票完整保留** ✓

按列切还正好 **72 / 72 格**，且 **PUMPKIN 带与 SUNFLOWER 带完整落在右半区** → 「Petal Gate 最大花瓣」与「南瓜整阵计数」都不需要跨机协调。

## 第 15 轮：字典缓存问题、向日葵模型、棋盘 16×16 重划

### 1. 用字典缓存南瓜状态？——不可行，可用数据直接否决
实测 `ticks/sweep 49466 ÷ 200 = 247` 个行动，`247 × 200 = 49,400 ≈ 49,466` —— **一轮扫描的 ticks 几乎 100% 都是行动**（每行动固定 200 ticks）。而 `get_entity_type()` / `can_harvest()` 各只花 **1 tick**，本来就是 1~2% 的开销。更关键的是**字典减少不了行动数**：`harvest()` 与 `plant()` 都必须无人机**物理站在那一格**上，所以"少检测"换不来"少跑腿"。**结论：不做。**

### 2. 向日葵的生长规则可能被误解 —— 已加诊断，两种模型下都不依赖
文档只保证「至少 7、最多 15 花瓣」「未成熟也能测」，**没有说花瓣会随时间增长**。所以有两种模型：
- (a) **随生长增长**：7 → 15，最终全带都是 15 → 每轮可割全部，产能极高
- (b) **种下时随机定死** ∈[7,15]：稳态下约 `N/9` 株处于最大值（N=36 时约 4 株/轮）→ 产量刚好被消耗吃掉 → 这正是 `power` 卡在 0 的成因

我此前的注释写「花瓣生长极慢」是**在未验证的情况下断言了模型 (a)**，这是错的。
**关键：代码逻辑（割当前全场最大的成熟株）在两种模型下都正确，而"加格数"在两种模型下都直接提升产能。**
新增 `sun_min`（全带最小花瓣）+ `sun_atmax`（处于最大值的株数）来区分：模型 (a) 下 `sun_min` 会逐渐升到 15，模型 (b) 下会长期停在 7~9。
**不能靠"割非最大的株"来提升产量** —— 文档说那会让「接下来收获的也只能获得普通数量」，会连锁污染。

### 3. 棋盘 16×16（256 格）→ 布局全部按 SIZE 重新推导
`SIZE=16, HALF=8`，左右半区各 128 格：

| 带 | 16×16 | 12×12（旧） |
|---|---|---|
| WOOD | 24（`SIZE//5`=3 行 × 8 列） | 12 |
| HAY | 40（`SIZE//3`=5 行） | 24 |
| CARROT | 64（剩 8 行） | 36 |
| PUMPKIN | **64（8×8 = HALF×HALF）** | 36（6×6） |
| SUNFLOWER | **64（8×8）** | 36（6×6） |

**推翻了一条旧结论**：`PUMPKIN_SIZE` 原来是 `min(HALF, 6)`，理由是「6×6 每格产出最优」。但 `n≥6` 之后每格产出**恒为 6**（`n²×6 / n²`），所以正确的推理是：**单次收割总量按 `n²` 增长，而成阵难度只按 `log(n²)` 增长 → 方阵越大越划算**。已改成 `PUMPKIN_SIZE = HALF`（16×16 时 8×8，基础 384 个/次）。
**顺带白拿**：向日葵带从 36 格**翻到 64 格**，正是第 2 条里"加格数"那一步，不需要额外腾格子。
`WOOD_ROWS` 从 `SIZE//6` 调到 `SIZE//5`：16×16 下胡萝卜 64 格每轮要吃 512 木材，木材带加厚到 24 格才稳。

### 2.7 定案：一次「最大花瓣」收割 = 8 点 power（BUILD 16 实测，22×22）

用户把棋盘扩到 **22×22**（Expand 会**重置整盘为草原**，`SIZE_OF_BOARD` 是启动时常量 → 不重启就会满屏 `不能在 Grounds.Grassland 上种植` 警告且全线停产）。重启后 BUILD 16 的逐刀读数给出了答案：

```
[sun] round 2  sec/round 49.65  alive 206  max_petal 15  harv 2  mature 206  min 7  atmax 2  matgate 2
               gain -48.99  hsum 16  hmax 8  hmis 0  rtot -110.31  jsum 0  jharv 0  expdone 1  wmin 0.18  pow 0
[sun] round 4  sec/round 64.77  alive 206  max_petal 15  harv 3  mature 206  min 7  atmax 3  matgate 3
               gain 7.05   hsum 24  hmax 8  hmis 0  rtot 7.05   pow 7.05
```

**1) 收割没坏，是产出极小**：`hsum / harv` = 16/2 = **8**、24/3 = **8** —— 每一刀**恰好 8 点 power**（`hmax 8`，`hmis 0`）。
   8 = **基础 1 × 8 倍加成**（lv_sun 1）。所以「8 倍」生效了，但**基础产出只有 1**：花瓣数**不参与产量**，它只是「够不够格吃 8 倍」的判据。文档里 `petals × 8` 的直觉是错的（`__builtins__.py` 的「5 倍」也是旧的）。
**2) 为什么 power 恒为 0**：带 power 时的耗电约 **2.2~2.6/秒**（round 2 净 -110.31/49.65 s）；而**没 power 时不耗电**（round 4 的量测遍净耗 0）—— 也就是「有电才 2 倍速，才烧电」。
   收入 = 每轮收割次数 × 8：旧策略（只割最大株）每轮只有 1~3 刀 = **8~24 点/轮**，抵不过每轮几十上百的耗电 → `pow` 永远 0 → 2 倍速永远吃不到。
**3) 顺带发现「垃圾株淤积」**：206 格里**只有 2~3 格**处于最大花瓣（`atmax 2`、`matgate 2`）。若花瓣在 [7,15] 上均匀，206 格该有约 23 格是 15 瓣 → 实际分布**极度偏向低花瓣**，且「只割最大株」的策略让 204 格**永不收割、永不重抽**，整片地被低花瓣株占满 → **稳态产出 ≈ 每轮 1~3 刀，与带子大小无关**。

**BUILD 17 的对策：整片轮转（`rot`）** —— 成熟就割、割完立刻补种，不再挑花瓣。
- 依据：「割错」的惩罚只是**下一次收割失去 8 倍**，在 base=1 的量级下最多损失 **7 点**，可以忽略；
- 收益：每轮收割次数 = 带子格数（206），实测访问速率 **412 次 / 64.77 s = 6.4 次/秒** → 6.4 点/秒 ≫ 2.6/秒 的耗电 → **2 倍速可持续**；
- 附加好处：每格都在重抽花瓣，高花瓣株不再淤积。
- 新增上报：`rot`（非最大株的收割数）、`g8`（拿到 8 倍的刀数）、`jpet`/`jpow`（本轮第一刀非最大株的**花瓣↔产出**配对，用来标定普通产出是 1 还是跟花瓣走）、以及独立一行 `[sun2]` 的**花瓣直方图** `h7..h15`；`[stat]` 加 `sun_cost`（向日葵升级下一级的成本；若为 -1 说明已满级，也就没有「靠升级放大产出」这条路）。

### 2.10 恐龙跑 v2（`dino_fast.py`）：直走 + 回路兜底

**实测确认文档口径**：`[dino] first target 8 4 from 0 0` —— 站在苹果上时 `measure()` 确实返回**下一颗苹果的坐标** ✓（v1 从来没用过这条，沿回路瞎撞 242 步/颗）。

**但 v2 第一版卡死**（跑了 2 分钟只有 3 行输出、之后再无动静）：目标不可达（苹果被蛇身围进口袋）或目标过期（走到坐标上没有苹果）时，旧代码退化成**「四向乱试」→ 原地随机漂移**，几千步吃不到一颗。教训：**兜底不能是随机 —— 必须有「保证覆盖全场」的搜索模式**。

**v3 的三级策略**（每级都有明确出路，`move()` 失败无惩罚所以最终以它为准）：
1. **直走**（`ST[4]==1` 且 `eaten*4 < CELLS*3`，即尾巴不到 3/4）：贪心先走差距大的轴 → 被挡就 BFS 求第一步 → BFS 也说不可达就**丢弃目标**进入模式 2。阈值取 3/4 而不是 1/2：后半程每步 tick 已很便宜，但每步的**语句开销**没变，回路的 242 步/颗 × 200 颗会变成几分钟的纯走位。
2. **哈密顿回路搜索**：沿回路走下一格，被挡就走上一格。回路覆盖全场 ⇒ **一定能踩到苹果**（苹果若长在蛇身弧内，等尾巴让开后回路会再经过它）。
3. **跟尾巴**：朝**尾尖**走（尾尖移动时一定让开 = 蛇类游戏经典脱困）。
   最后四向挑「不是回头路」的；真四向都动不了 = 蛇填满农场 → 收工结算。
   诊断计数：`mode direct/cycle/tail`、`bfs_fail`、`dropped_targets`，另有 `stale target` 打印。

**其他调整**：`MAX_APPLES = 420`（实测蛇能填到 77~85%，再多只是空转）；尾巴用 `OCC` 计数表做 O(1) 占位查询（原先是每次 O(尾巴长度)，BFS 会对每个邻居查一次 → 20 万次 × 460 长度会把省下的时间全吃回去）。

**第一轮实测（v3 仍卡）**：
```
[dino] first target 1 4 from 0 0
[dino] stuck at step 476 eaten 29 pos 3 2 cactus 5048
[dino] eaten 420 bones_gained 841 total_bones 30109 mode direct/cycle/tail 470 5 0 bfs_fail 1 dropped_targets 1
```
**直走是对的**（470 步吃 29 颗 ≈ 16 步/颗 ✓ 比回路的 242 步/颗快 15 倍），但**尾巴只有 29 节就把自己围死了**：贪心直走会把身子卷成一个圈，头被封在里面、四向全是身体（`pos 3 2` 靠角，31 颗苹果只换来 841 骨头）。这是贪心寻路的经典陷阱 —— **必须加安全检查**。

**v4 的两道安全检查 + 单向切换**：
- **检查 1（永远做，只要 4 次占位查询）**：走完这一步后，新位置至少还要有一个能走的邻居（**要排除刚离开的那一格** —— 它立刻变成身体）。挡掉「一步进死胡同」。
- **检查 2（`ST[1] >= 12` 才做）**：从候选格做**有上限的洪水填充**（最多 `SPACE_LIMIT = 32` 格，用世代号免去每次清零的 484 条语句）；可达空格必须 ≥ `尾巴+6`（超过 32 就取 32）。挡掉「钻进会被自己围死的小口袋」。
- **单向切换**：直走一旦失败（安全检查否决 / BFS 说不可达），就置 `ST[6] = 1` **之后全程走回路**（回路覆盖全场 = 一定找得到），不再来回切换 —— 实测 29 节就能被贪心围死，安全优先。
- 新增诊断：`switch to cycle mode at eaten N deadend/pocket/bfs_fail …` 与收尾的 `guard deadend/pocket` 计数，用来判断该不该调阈值。

**v4 上线后立刻暴露（用户：「第一次吃到苹果时就开始走哈密顿回路了」）**：直走在**第一次**尝试时就被否决 → v4 的「一次失败就永久切回路」把整轮按回 v1 速度。两个设计错误：
1. **检查 1 的排除写法不可靠**：我写的是 `if not (ax == cx and ay == cy):` —— 在这个自研解释器里，**`not` 与比较/`and` 混用的优先级没有先例可循**（main.py 里只用过 `not can_harvest()` / `not in_pumpkin_zone(...)` 这种纯函数调用）。若它恒为真（即恒排除）→ `free_n` 永远是 0 → 每一步都被判死胡同 → 直走全废。已改成**纯嵌套 if**（`is_old` 标志），并把这段抽成 `free_neighbors(nx, ny, cx, cy)`。
2. **单向切换太脆**：单次失败可能只是这一步被挡（换条路就行），不该锁死整轮。已改成**连续 5 次**直走失败才切回路（`ST[7]` 计数，成功即清零），每次否决都打印原因/位置/尾巴长度。

**v5 的加固**：
- **启动自检**：站在开阔的起点上，`free_neighbors(1,0,0,0)` 必须 > 0、`space_ok(1,4)` 必须 = 1；任何一项不符合预期就把对应的安全检查**关掉**并打印 `v5 self-test: guardN disabled`。这样解释器怪癖只会让检查失效，不会让整轮退回 v1 速度。
- **版本标记**：打印 `=== dino_fast v5 start ===` 与 `v5 guards on: 1 1` —— 游戏会缓存编辑器缓冲区，没有版本号就无法确认跑的是哪一版（main.py 的 `BUILD` 就是为此加的）。

**v6：洪水填充太贵 —— 换成廉价检查 + 冷却（用户反馈「检查 2 阶段特别慢，而且到一定长度卡得更严重」）**

成本账：v5 的检查 2 是**有上限的洪水填充**，`need` 封顶 32 格，而每格要展开 4 个邻居、每个邻居都要 `tail_blocked`（约 12 条语句）⇒ **单次约 1,600 条语句，每个候选步最多两次 = 每步 3,200 条**。而一步的移动成本只有 `400 × 0.97^k`（k=12 时 277 tick）—— 检查比移动贵一个数量级，无人机看起来就是在爬。

「到一定长度更卡」的第二个原因：尾巴一长，直走**每一步都失败**，于是每步都要**重付**「洪水填充 + BFS（每次还要 484 条语句清零 visited！）+ 回路走位」三份开销 ⇒ 越到后面越慢。

修法：
1. **删掉洪水填充**，换成 **O(4~16) 次查询**的廉价检查：
   - `escape2(nx,ny,cx,cy)`：新位置要有「两步活路」（空邻居的空邻居）⇒ 挡掉 1 格 / 2 格深的死口袋（v3 就死在 2 格口袋里）；
   - `body_neighbors(nx,ny) >= 3` 判「窄缝」，一宽格的夹缝迟早封死。
2. **BFS 访问标记改世代号**（省掉每次 484 条清零）+ **展开格数封顶** `BFS_CAP = 260`。
3. **直走失败后冷却 20 步**（`ST[8]`；吃到苹果时清零 —— 那时 measure() 给了新目标，值得立刻再试）。这样长尾巴阶段不会每步重付三份开销。
4. **空格 < `TIGHT_FREE = 64` 直接常驻回路**（`CELLS - ST[1] < 64`，一行比较就够），空间太紧时直走只会白烧语句。
5. 自检与版本号跟进到 v6（`escape2` / `body_neighbors` 在开阔起点的判定必须为「安全」，否则自动关掉该检查）。

### 2.12 v6 实跑结果 + v7：兜底也必须带守卫、BFS 上限不能低于棋盘格数

```
[dino] v6 guards on: 1 1 1
[dino] v6 direct rejected at eaten 21/22/23/34 … bfs_fail 1..4
[dino] stuck at step 566 eaten 34 pos 5 12
[dino] eaten 420 bones_gained 1156 total_bones 31265 mode direct/cycle/tail 491 72 2 guard d/n 0 0
```

两个读数直接定位了问题：
1. **`guard d/n = 0 0`**：守卫**一次都没拦过**（说明它们没误伤），但无人机还是被盘死了 ⇒ 陷阱不是「直走」造成的；
2. **`cycle 72`**：陷阱发生在**兜底阶段**。因为**守卫只管直走，兜底用的还是不带守卫的 `try_move`** —— 门锁了窗没锁。苹果不可达时会被推进兜底，长时间的裸走位就把自己盘死了。

另外 `bfs_fail 1..4` 本身可疑：尾巴才 21~34 节、棋盘空着 93%，苹果**不可能真的不可达** —— 是 v6 新加的 `BFS_CAP = 260` **小于棋盘格数 484**，BFS 常在被截断时返回「无路」⇒ 误判不可达 ⇒ 直走被放弃 ⇒ 被推进兜底 ❌。两个 bug 互相放大。

**v7 三处修改**：
1. **兜底阶梯全部带守卫**，顺序改为「跟尾巴(守卫) → 回路(守卫) → 跟尾巴(裸) → 回路(裸) → 任意方向」，跟尾巴排在前面（尾尖必然让开 = 保命优先）；统一走 `move_or(d, grew, safe)`。
2. **`BFS_CAP = CELLS + 4`**（不得小于棋盘格数）；调用频率改由「直走失败冷却 20 步」控制，不用靠截断省钱。
3. **窄缝检查收紧**：尾巴 ≥ 24 节时门槛从「四邻被占 ≥3」改为 **≥2**（实测三十几节就能被盘死，而「两侧都是身体」正是入口）。

版本标记升到 v7（`v7 start` / `v7 guards on` / `v7 direct rejected` …），方便核对游戏里跑的是哪一版。

### 2.13 v7 实测 + v8：**直走只在前 26 颗用，其余交给「可证明安全」的回路**

v7 结果（`bfs_fail 0` —— BFS 截断那个 bug 修好了 ✓，守卫也开始工作 ✓）：
```
[dino] v7 direct rejected at eaten 31 … deadend 1 narrow 5
[dino] stuck at step 708 eaten 40 pos 2 3     （guard 计数：deadend 7 narrow 15 —— 全挤在最后 7 步）
mode direct/cycle/tail 681 13 11
```

**三次卡死的规律**：v3 在 29 颗、v6 在 34 颗、v7 在 40 颗被自己盘死，位置都在角落附近 `(3,2)/(5,12)/(2,3)`。结论：
1. **廉价守卫治不了这个病**：我的 `escape2` 只验「两步活路」，而**比两步更深的死口袋照样能把头封在里面**（头钻进 3~4 格的口袋后，入口那格就变成身体了）。守卫只在最后 7 步才连续报警 —— 那时陷阱已经成型。
2. **能治病的检查（洪水填充／能否摸到自己的尾尖）正是实测「特别慢」的那一版**：填充一次约 1,600 条语句，而游戏里一条语句约 5~15 tick（由 v1 实测 198 颗×25,344 步÷540 秒≈128 tick/步反推），即每步 1~2 万 tick，而一步移动才 19~400 tick ⇒ **贵一个数量级，不能用**。
3. 因此「又快要又安全」在**每步只能花几十条语句**的预算下是做不到的；能证明安全的只有一条路：**严格沿哈密顿回路**（v1 在 16x16 实测安全吃到 198/256）。

**v8 的两段式（当前版本）**：
- **阶段 A（`eaten < DIRECT_MAX = 26`）**：直走 + 守卫。它省下的时间几乎全在这里 —— 移动成本 `400 × 0.97ᵏ`，k=26 时已衰减到 0.45，前 26 颗的总移动 tick ≈ 14 步 × 400 × Σ0.97ᵏ ≈ 9.5 万，而同样这些颗走回路要 ≈ 160 万 tick。
- **阶段 B（其余）**：先走 2 颗「带守卫的回路」（≈480 步）把身体拉回回路上 —— 身体只保留最近 `ST[1]` 步的轨迹，所以两轮之内必然完全对齐；之后切 **B2 极简回路**（`bare_cycle_move()`：不维护尾巴模型、不做守卫、不查表，只算下一格 + `move()`），安全性由 v1 的证明保证（身体是回路上一段连续弧且长度 < 总格数 ⇒ 回路下一格必然不在身上）。
- 兜底阶梯的顺序按阶段区分：**直走期「跟尾巴」在前**（保命优先），**对齐期「回路」在前**（回路才是推进对齐的动作）。

预期：~8 分钟走完 ~420 颗 = **17.6 万骨头**，并且能跑完（对比 v7 的 40 颗 / 1,600 骨头）。如果这条也不稳，退路是直接用 v1（`dino_bones.py`，纯回路、已验证）。
