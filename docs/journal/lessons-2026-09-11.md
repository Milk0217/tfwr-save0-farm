## 一、改游戏脚本的铁律（两次事故换来的，血泪级）

1. **绝不用 PowerShell 的 `-replace` + `Set-Content` 往返改脚本**。实测两次：
   - 一次吞掉 13 行、把代码并进注释（`goto(BUSH_X,BUSH_Y)`、`i = 0`、`facing = 1` 全失效）；
   - 一次把 `while True:` 整行删掉（语法错）。
   **只用 `edit`/`write` 工具，或 Python（显式 `utf-8` + `newline="\n"`）**。
2. **改前必须重读文件**：游戏会在每次跑完后用它的编辑器缓冲区**回写** `.py`，外部改动可能被覆盖。
3. **每个脚本都要有版本标记并打印**（`BUILD = N` / `=== xxx vN start ===`）。没有它就无法判断
   "跑的是哪一版"—— 这一轮多次出现"改了却没生效"的假象。
4. **改完三连验证，缺一不可**：
   `python -m py_compile 文件.py` → `python tools/audit_save0.py` →（布局/下标类改动）
   **几何自检**（方阵两两间距、下标范围）。
5. **补丁先核对锚点命中数，再写文件**：命中数不是 1（或 0）就 `ABORT`，**不写**。
   这一条本轮救过两次：一次锚点写错（`goto(cactus_x(0),0)` 实际 3 处）安全中止、文件未动；
   一次在 `maze_gold` 上避免了重复事故。
6. **一次只做一件"能跑能回退"的事**：删代码与换结构分批；跨文件改动必须一次做完再验证。

## 二、这个游戏语言的坑（会静默毁掉整轮）

| 坑 | 症状 | 对策 |
|---|---|---|
| **列表下标越界** | 整轮直接中断，只打一行 `Error` | 静态体检；**重复声明**是最常见根因（`CHECK=[1,1]` 覆盖了 `[1,1,1]`） |
| **`not (A and B)` 混写** | 求值不符预期（守卫恒判死胡同 → 快路径全废） | 一律拆成**嵌套 if** |
| **`swap(dir)` 不移动无人机** | 交换 N 次却毫无变化（同一对来回换） | `swap` 后紧跟同方向 `move` |
| **没有共享内存** | 副机读全局恒为初始值（power 恒 0、统计恒 0） | 跨机只走 `spawn_drone(f, 参数…)` 与 `wait_for(d)` 返回值；**要打印的量必须显式赋值** |
| **import 语义**（`docs/scripting/import.md`） | 怕跨模块派副机会丢状态 | 每次无人机执行是**独立程序执行** ⇒ `import` 在它自己内存里重跑 ⇒ **模块状态每架一份**，跨模块安全；但只用 `import X`，**不要** `from X import *` |
| **矩形/合并产量口径变化** | 两块 6×6 紧挨 ⇒ 连成 12×6，`pyield` 从 13,824 变 27,648 | 方阵之间**必须留 ≥1 格间隔**，并把间距自检写进启动流程 |

## 三、性能方法论（本轮最大的收获）

1. **先测量，再优化**。本轮被实测推翻的猜想至少三个：
   - "金币用 4 个 11×11 小迷宫能快 3.7 倍" → 实测**更慢**（金币减半，固定开销不减半）；
   - "向日葵格数越多收入越高" → 收入 = **访问速率 × 1.13**，与格数无关；
   - "一次 6×6 仙人掌 = 1,296" → 实测 **5,184（4 倍）**，"一次南瓜 = 216" → 实测 **13,824（64 倍）**。
2. **成本结构**：动作 = 200 tick；语句 ≈ 5~15 tick ⇒ **每步的语句开销常常比动作还贵**。
   推论：**减少步数**（少访问、缓存状态、别每步做搜索）比"每步写得更聪明"重要得多。
   反例：洪水填充安全检查 ≈ 1,600 条语句/步，比一次移动贵一个数量级 → 实测"特别慢"，必须删。
3. **收入几乎总是"访问速率受限"，不是"地块受限"**：地块多不等于产出多，除非再生速度跟得上
   （向日葵 5 秒、胡萝卜 6 秒）。**判断饱和**：`地块数 ÷ 再生时间` 对比 `无人机数 × 每秒访问数`。
4. **闲置的无人机不耗电，派到饱和地块上的会**（每 30 次行动耗 1 点 power）⇒
   "把 32 架全用上"经常是**错的**：会抽干 power、丢掉 2 倍速，全场反而更慢。
5. **超线性产量要用对切法**：仙人掌一块 n 格连通区产量 = `4n²` ⇒
   所有区域产量和 = `4Σnᵢ²`（凸）而排序耗时 ∝ `n^1.5` ⇒ **吞吐 ∝ √(区域数)** ⇒ 尽量多切几块。
6. **power 收支**：收入 = 收割刀数 × ~1.13（普通刀 1 点、约 11% 吃 8 倍）；耗电随"动作数"线性增长
   ⇒ 想省电就**砍掉最大的那块动作开销**（本轮砍掉主机每轮 128 格读票往返，直接省掉全场最大一笔）。

## 四、架构与算法

1. **不要全局栅栏**：每个地块跑自己的无限循环，互不等待。南瓜的概率门（整阵全熟）访问越频繁收得越多，
   等最慢的工人等于白白降低收割频率。
2. **概率门必须逐单元独立结算**：`0.8^36` 已是 0.03%，几块合判会低到几乎为零 ⇒ 直接停产。
   凡是"全单元同时满足"的门，状态机都要按单元拆。
3. **两段式算法**：既想要速度又想要安全时，把**快但有风险的阶段限制在实测危险线以内**
   （恐龙跑：前 26 颗问路直走，其余走可证明安全的哈密顿回路；实测直走会在 29/34/40 颗把自己盘死）。
   配套：危险阶段的**守卫要有自检**（在已知安全的输入上必须判"通过"，否则自动关掉该守卫）。
4. **随机兜底 = 没有兜底**：目标不可达时退化成"四向乱试"会让无人机原地漂移几千步；
   兜底必须是**有覆盖保证的搜索**（哈密顿回路覆盖全场）。
5. **状态机选对判据**：成熟的作物不会再枯死 ⇒ "存活且成熟"是单调状态 ⇒ 只访问"待确认"的格子，
   把 144 动作/轮压到 ~16。
